Joins and Subqueries: The Join Pattern Selector

Prepared by Dr. Gorkem Kar

Real data lives across many tables. Answering a real business question — who bought what, who's never ordered, whose numbers don't reconcile — means stitching tables back together at query time. This playground is about picking the right tool for that: the five ways two tables can meet, the NULL trap hiding inside NOT IN, and the semi-join/anti-join/window-function patterns that separate a working query from a fast, correct one.

Foundations

Choosing the Right Join

A join is a matchmaking process: you have a left table, a right table, and a rule for how rows pair up. The type of join you pick determines what happens to the rows that don't find a match. The whole decision comes down to one question: which unmatched rows do you want to keep?

Join typeA-only rowsMatched rowsB-only rowsUse it when
INNER JOIN✗✓✗You need pairs that exist on both sides
LEFT JOIN✓ (NULLs on B side)✓✗You want every A row, plus B's info if any exists
RIGHT JOIN✗✓✓ (NULLs on A side)Same as LEFT, from B's perspective (rarely used — most people just flip the table order and use LEFT)
FULL OUTER JOIN✓✓✓You want every row on both sides — a reconciliation
Anti-join (WHERE NOT EXISTS)✓ (unmatched only)✗✗You want the gaps — A-rows with no B partner
Semi-join (WHERE EXISTS)✗✓ (A's columns only, deduped)✗You want to filter A by "has a match in B," without importing B's columns

The strictest is INNER JOIN: if a row on either side has no match, it's discarded entirely. LEFT JOIN is more forgiving — "give me everything from the left table, and if there's a match on the right, show it; if not, put NULLs there." That's how you find the gaps: every customer, including the ones with zero orders.

Foundations

The Wrong-LEFT-JOIN Trap

This is the single most common LEFT JOIN bug, and it shows up at every seniority level: a WHERE filter on a right-side column silently turns your outer join back into an inner join.

Why it happens: WHERE runs after the join. For customers with no matching subscription, every subscription column — including status — is NULL. The comparison NULL = 'active' evaluates to Unknown, and WHERE drops Unknown just like it drops False. So every unmatched left-side row gets silently filtered out, even though the whole reason you wrote LEFT JOIN was to keep it.
wrong_left_join_vs_fixed.sql

The fix is always the same: move the filter on the right-side table into the ON clause, so it's applied during matching rather than after. ON s.cust_id = c.cust_id AND s.status = 'active' lets non-subscribers stay in the result with NULL subscription columns, which is what "every customer, with active-subscription info if any" actually means.

Foundations

Subqueries: Scalar, Table, Correlated

Sometimes a join isn't the most natural way to express a question — you need the result of one query to filter or compute inside another. A scalar subquery returns exactly one value (a single number, a single string) and can be used anywhere a constant would go — "find products priced above the average" needs the average computed first, and that average can't be a hardcoded literal. A table subquery returns a list or a whole temporary result set, often paired with IN or as a joinable derived table.

Both of those run independently: the database evaluates the inner query once and hands the result to the outer query. A correlated subquery is different — the inner query references a column from the outer query's current row, so it must run once per row the outer query processes, like a for-each loop. That's what makes "the most recent order for each customer" or "the first event for each user" possible, at the cost of re-scanning the inner table once per outer row.

The NULL Trap

The NOT IN / NULL Trap

This is the subquery equivalent of WHERE column = NULL — a trap that has bitten every senior engineer at least once. You want customers who've never ordered:

WHERE cust_id NOT IN (SELECT cust_id FROM orders)

This works right up until a single row in orders has a NULL cust_id — a guest checkout, say, where no customer was ever attached. As soon as that happens, NOT IN silently returns zero rows, for every customer, even the ones who obviously have never ordered anything.

not_in_vs_not_exists_vs_leftjoin.sql
Why it fails: x NOT IN (a, b, NULL) is really x != a AND x != b AND x != NULL. The last comparison is always Unknown. TRUE AND TRUE AND UNKNOWN is Unknown — and WHERE only keeps rows that are True. One NULL anywhere in the subquery's results poisons the entire predicate, for every outer row, regardless of whether that row's own value would obviously qualify.

NOT EXISTS checks for the presence of a row, not value equality, so it's completely immune to NULLs on either side — and it's often faster besides, since the database can stop scanning the instant it finds one match. LEFT JOIN ... WHERE right.col IS NULL is the other safe pattern. Prefer NOT EXISTS by default; reach for plain IN/NOT IN only when you can guarantee the subquery's column is NULL-free.

The NULL Trap

Semi-Joins and Anti-Joins

When you filter table A using EXISTS or IN against table B, you're performing a semi-join: you use B purely as a filter, and B's columns never appear in the output, and A's rows are never duplicated even if several B rows match. An anti-join is the mirror image — rows from A that have no match in B — the "find the gaps" pattern from the section above.

The tempting alternative — INNER JOIN plus DISTINCT — gets the same rows, but only after actually joining in (and then discarding) every matching row from B. A true semi-join never materializes B's rows at all.

semi_join_products_ever_sold.sql

Widget has two sales rows. EXISTS and plain IN each return it exactly once — that's the semi-join property. The plain INNER JOIN without DISTINCT, shown last, returns Widget twice — once per matching sale — which is almost never what "products that have sold" is supposed to mean.

Patterns That Scale

Latest-Per-Group: Correlated Subquery vs. Window Function

"For each customer, show their most recent order" is a hierarchical question — one row per customer, but the value depends on which customer. A correlated subquery answers it directly: for each row of customers, re-run MAX(order_ts) WHERE cust_id = <this row's id>. It reads cleanly, but on a million-row customer table, that's a million separate subquery evaluations against orders.

A window function answers the same question in a single pass: rank every order within its customer's partition by recency, then keep only rank 1.

latest_order_subquery_vs_window.sql

Both queries return the same rows here. The difference is scaling behavior: the correlated subquery re-scans orders once per customer; ROW_NUMBER() OVER (PARTITION BY ...) scans orders exactly once, ranks everything in one pass, and the outer query just filters to rn = 1. Prefer the window-function shape once the tables get large.

Patterns That Scale

FULL OUTER JOIN: Finding Discrepancies

FULL OUTER JOIN is the most inclusive join: it keeps every row from both sides, filling in NULLs wherever a match is missing on either one. Its best use case is a reconciliation — two systems that are supposed to agree, and you want to know exactly where they don't.

full_outer_join_discrepancies.sql
Portability note: FULL OUTER JOIN (and RIGHT JOIN) only work in SQLite from version 3.39 (2022) onward — this playground's engine is new enough. MySQL has never supported FULL OUTER JOIN at all; the standard workaround there is a LEFT JOIN UNION RIGHT JOIN (or, more simply, LEFT JOIN ... UNION SELECT ... RIGHT-side-only rows). PostgreSQL and SQL Server have always supported it directly. Check your target engine before relying on it.
Patterns That Scale

The Accidental Cartesian Product

Forget the JOIN keyword, forget the ON clause, forget the WHERE — and list two tables separated by a comma — and SQL doesn't error. It gives you every possible pairing of rows: the Cartesian product. Each row of A is paired with every row of B, whether or not they're related in any way.

accidental_cartesian_product.sql

10 rows × 20 rows = 200 rows here. Scale that pattern to a 10,000-row users table and a 50,000-row orders table and a missing ON clause produces 500,000,000 rows — which is either a query that never finishes, or one that silently eats all the memory on the box. A missing join condition on small test tables is a correctness bug; the same missing condition on production tables is an incident.

Practice Problems

1. Self-join for manager names

Given employees(emp_id, name, mgr_id) where mgr_id is a foreign key back to employees.emp_id (NULL for the CEO), write a query that lists every employee alongside their manager's name. Ensure the CEO appears in the output even though they have no manager.

▸ Reveal answer
SELECT e.name AS employee, m.name AS manager FROM employees e LEFT JOIN employees m ON m.emp_id = e.mgr_id;
  • Self-join: employees joined to itself using two aliases (e for employee, m for manager).
  • LEFT JOIN (not INNER): the CEO has mgr_id IS NULL, so no matching row exists in m. LEFT JOIN preserves the CEO in the output with manager = NULL.
  • An INNER JOIN here would silently drop the CEO.

2. Which pattern is safe under NULLs?

Given a users table and a banned_users table, which of these queries is safe if banned_users.user_id can contain NULL?

(a) WHERE id IN (SELECT user_id FROM banned_users)   (b) WHERE id NOT IN (SELECT user_id FROM banned_users)   (c) WHERE EXISTS (SELECT 1 FROM logs WHERE logs.user_id = users.id)

▸ Reveal answer
  • (a) Safe. IN with a NULL in the subquery becomes Unknown for that one comparison, but if a non-NULL match exists elsewhere in the list, the row is still returned. Extra NULLs are effectively ignored, not toxic.
  • (b) Dangerous. As soon as banned_users has one user_id IS NULL, the entire NOT IN becomes Unknown for every user, returning zero rows. Rewrite as WHERE NOT EXISTS (SELECT 1 FROM banned_users b WHERE b.user_id = users.id).
  • (c) Safe. EXISTS checks for row presence, not value equality — NULLs in logs.user_id simply don't match anything, they don't collapse the whole predicate. This is exactly why NOT EXISTS is the recommended replacement for NOT IN.

3. Counting rows across join types

Given A = {1, 2, 3, 4, 5} and B = {4, 5, 6, 7, 8} as tables each with one column id, how many rows does each query return?

(a) A INNER JOIN B ON A.id = B.id   (b) A LEFT JOIN B ON A.id = B.id   (c) A FULL OUTER JOIN B ON A.id = B.id   (d) A CROSS JOIN B

▸ Reveal answer
  • (a) 2 rows — only {4, 5} match on both sides.
  • (b) 5 rows — every A row survives: 3 unmatched (1, 2, 3) plus 2 matched (4, 5). Unmatched rows get NULL for B's columns.
  • (c) 8 rows — 2 matched, plus 3 unmatched from A, plus 3 unmatched from B.
  • (d) 25 rows — 5 × 5 = every possible pair. Cross joins scale multiplicatively, which is exactly why accidentally omitting an ON clause on large tables is catastrophic.

4. Correlated subquery vs. JOIN + GROUP BY

You want customers whose latest order is over 500. Write it two ways: (a) using a correlated subquery, (b) using a JOIN + GROUP BY. Which is likely to run faster on a large orders table with an index on cust_id?

▸ Reveal answer

(a) Correlated subquery:

SELECT c.cust_id, c.name FROM customers c WHERE (SELECT total FROM orders o WHERE o.cust_id = c.cust_id ORDER BY o.order_date DESC LIMIT 1) > 500;

(b) JOIN + GROUP BY, then filter:

WITH latest AS ( SELECT cust_id, MAX(order_date) AS max_date FROM orders GROUP BY cust_id ) SELECT c.cust_id, c.name FROM customers c JOIN latest l ON l.cust_id = c.cust_id JOIN orders o ON o.cust_id = l.cust_id AND o.order_date = l.max_date WHERE o.total > 500;

Version (b) is usually faster on large tables — it scans orders once to compute latest, then joins. The correlated subquery in (a) effectively re-evaluates per customer. On a million customers with millions of orders, the difference can be minutes versus milliseconds. The optimizer sometimes rewrites (a) into something like (b), but you can't rely on that — write the cleaner shape yourself.

5. Why did the NULL-status rows disappear?

You wrote WHERE status NOT IN ('shipped', 'cancelled') intending to find pending/processing orders. When you run it, orders where status IS NULL are missing from the result. Why, and how do you fix it?

▸ Reveal answer

NULL NOT IN ('shipped', 'cancelled') evaluates to Unknown, because comparing NULL to any value is Unknown, and Unknown AND ... is Unknown. WHERE only keeps True rows, so NULL-status rows are dropped.

Fix — explicitly handle NULL:

WHERE (status IS NULL OR status NOT IN ('shipped', 'cancelled'))

Or, if NULL status is a data-quality bug and shouldn't exist, add a CHECK constraint to the schema going forward and clean up the existing NULLs. Either fix is defensible — the query fix recovers from bad data; the schema fix prevents it.

Apply It

In the Interview

Joins are the single most-asked SQL topic in coding rounds. Every top company's SQL screen tests joins first.

The classic SQL-round question. Given a users table and an events table (with a user_id FK), find users who signed up but never triggered a purchase event. The correct answer uses either LEFT JOIN ... WHERE ... IS NULL (anti-join) or NOT EXISTS. NOT IN is a trap — if any user_id in events is NULL, the query returns zero rows silently. Interviewers know this and use it as a filter for careful vs. sloppy candidates.

The follow-up. "Now find users whose first purchase happened within 7 days of signup." This is a classic "for each user, the first purchase" pattern — either a correlated subquery (SELECT MIN(event_ts) ... WHERE user_id = u.user_id), or a window function (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY event_ts) filtered to rn = 1), or a JOIN with MIN(event_ts) GROUP BY user_id. Verbalize the trade-offs: window functions read cleanly, aggregations are usually cheaper on large data.

Watch for the "wrong LEFT JOIN" trap. A very common bug at all seniority levels:

-- BROKEN: WHERE on the right side of LEFT JOIN silently drops unmatched rows SELECT u.user_id, s.plan_tier FROM users u LEFT JOIN subscriptions s ON s.user_id = u.user_id WHERE s.plan_tier = 'pro';

The filter runs after the join, and the LEFT JOIN's NULL rows fail s.plan_tier = 'pro', so they're silently dropped — turning the LEFT JOIN back into an INNER JOIN. The fix is to move the filter into the ON clause:

LEFT JOIN subscriptions s ON s.user_id = u.user_id AND s.plan_tier = 'pro';

Being able to spot this in a code review is a favorite interviewer signal.

Rule of thumb for interviews.

  • •Column from both sides → JOIN.
  • •Filter existence, no columns from the other table → EXISTS.
  • •Filter absence → NOT EXISTS (never NOT IN, unless the subquery is guaranteed NULL-free).
  • •"For each X, the latest Y" → window function (ROW_NUMBER() OVER (PARTITION BY x ORDER BY y_ts DESC)).

Verbalize which one you are using and why. Silent code loses the round even when it runs.

2026 Status

In 2026: What Has Changed

Join patterns are stable; what changed is how often an optimizer rewrites them for you.

  • LATERAL joins let a subquery reference columns from the table to its left — the clean way to express 'top N per group'.
  • Semi- and anti-joins are the shapes to reach for instead of IN / NOT IN whenever NULLs are possible.
  • Decorrelation means a correlated subquery often compiles to a join — but only when the pattern is provably equivalent.
  • Duplicate amplification is the most common join bug: joining a table with two matching rows doubles the row count and silently inflates every aggregate downstream.

Choosing the right join shape is usually the difference between a query that is correct and one that is merely close.
