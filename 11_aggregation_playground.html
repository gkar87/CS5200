Aggregation, GROUP BY, and HAVING

Prepared by Dr. Gorkem Kar

A raw table has details; a business decision needs a number. Aggregation is the bridge. COUNT, SUM, AVG, MIN, MAX turn ten million rows of transactions into the kind of report a CFO can read. GROUP BY breaks the data into meaningful buckets before those functions run; HAVING filters the buckets afterward. Nailing these three ideas is what separates someone who can query data from someone who can report on it.

Foundations

The Big Five Aggregates

Aggregation is the art of collapsing data — taking a pile of rows and squashing them into a summary. That requires a shift in how you picture your tables: you're no longer looking at a list, you're looking at a collection of buckets.

  • COUNT — how many items are in the set.
  • SUM — adds up every value in a numeric column.
  • AVG — the arithmetic mean.
  • MIN / MAX — the smallest / largest value.

Run SELECT SUM(total_price) FROM orders; and the database doesn't hand back a table with thousands of rows — it returns a single row with a single value. Every row has been consumed to produce that one result.

Foundations

The NULL Trap

NULL means "unknown or missing," and aggregate functions generally ignore it. If a users table has some rows with no age entered, AVG(age) does not treat the missing ages as zero — it removes those rows from the calculation entirely: AVG = SUM(non-NULL values) / COUNT(non-NULL values).

avg_ignores_null.sql

The single most common point of confusion: COUNT(*) counts every row that matches your criteria, full stop. COUNT(email) only counts rows where email is not NULL. With 100 users and 90 emails on file, COUNT(*) returns 100; COUNT(email) returns 90. Want the size of the group? Use the asterisk. Want to know how many people actually filled in a field? Use the column name.

The Logic of Buckets

Aggregation becomes genuinely useful once you stop squashing the whole table and start squashing specific sections of it — that's GROUP BY. Think of it as a sorting machine: GROUP BY department tosses every row into a bucket labeled by its department, and only once every row has a bucket do the aggregate functions run — one calculation per bucket.

SELECT region, SUM(amount) FROM sales GROUP BY region;

A critical rule: every column in your SELECT list must either be inside an aggregate function or listed in GROUP BY. SELECT region, salesperson, SUM(amount) ... GROUP BY region is a contradiction — SQL knows how to squash amount and how to group by region, but there might be fifty salespeople in the North bucket, and nothing tells it which one to show you.

SQLite quirk — it doesn't actually enforce that rule. Standard SQL (and PostgreSQL, and MySQL in strict mode) reject a bare, non-aggregated, non-grouped column with an error. SQLite instead applies a documented extension: for a bare column paired with MIN() or MAX(), it deterministically returns the value from the same row that produced that extreme — genuinely useful. Paired with SUM(), COUNT(), or AVG(), though, the bare column's value is picked from an arbitrary row in the group — not an error, not necessarily the first or last row, just unspecified. Filtering

Filtering: WHERE vs. HAVING

Both filter data, but at different stages of the pipeline. The order the database actually executes a query is not the order you write it in:

StageClauseWhat it filtersCan it see aggregates?
1FROMpicks source table(s)—
2WHEREindividual rows❌ No — groups don't exist yet
3GROUP BYcollapses rows into buckets—
4HAVINGwhole groups✅ Yes — that's the whole point
5SELECTcomputes final columns—
6ORDER BYsorts—

That's why an aggregate expression can only appear in HAVING, never in WHERE — by the time HAVING runs, the groups exist; when WHERE runs, they don't.

where_cannot_see_aggregates.sql

WHERE filters the input (raw rows). HAVING filters the output (bucketed summaries). One nuance: standard SQL evaluates HAVING before SELECT, so relying on a SELECT-list alias inside HAVING is dialect-dependent — SQLite happens to allow it, but PostgreSQL and others may not in every context. Safer to repeat the aggregate expression.

Worked Example: Trace a Query Through Execution Order

Given this sales table:

regionproductyearamount
NorthWidget2026100
NorthWidget2026100
NorthGadget2026200
SouthWidget202680
SouthGadget2026NULL
EastWidget2025500
SELECT region, SUM(amount) AS total FROM sales WHERE year = 2026 GROUP BY region HAVING SUM(amount) > 100 ORDER BY total DESC;

Trace it: FROM starts with all 6 rows. WHERE year = 2026 drops East's 2025 row — 5 remain. GROUP BY region buckets North into {100, 100, 200} and South into {80, NULL}. HAVING SUM(amount) > 100 computes each bucket's sum — North totals 400 and passes; South totals 80 (the NULL is silently ignored, not treated as zero) and fails. Only North survives to SELECT.

worked_execution_trace.sql

If you needed South's NULL to count as zero, you'd write SUM(COALESCE(amount, 0)) instead — that changes South's total to 80, still failing here, but the distinction matters when a NULL-heavy group is close to the threshold.

COUNT(DISTINCT user_id) — how many unique users gave feedback? COUNT(DISTINCT score) — how many distinct score values appeared? Worked Examples

Worked Example: Cohort Retention (Multi-Level Aggregation)

Every SaaS and consumer product asks the same question: "of the users who signed up in a given week, how many are still active N weeks later?" This is cohort retention analysis, and it lives entirely in the world of aggregation — but it needs two levels of it: bucket users into signup cohorts, then separately bucket their activity, then divide one by the other.

users(user_id, signup_date) events(user_id, event_ts, event_type)

The reference article's version uses PostgreSQL's DATE_TRUNC('week', ...) and DATEDIFF('week', ...) — both are non-standard, Postgres-flavored functions. SQLite has no DATE_TRUNC or DATEDIFF at all; the cell below rebuilds the exact same four-step logic with SQLite's own date functions (date(..., 'weekday 0', '-6 days') for a Monday-anchored week, julianday(...) for the day-difference math) so it can actually run.

cohort_retention_sqlite.sql
Where this pattern breaks new practitioners:
  • Forgetting DISTINCT in the activity CTE — a user with 100 events in one week counts 100 times, wildly inflating retention.
  • Grouping on the raw timestamp instead of the truncated week — every event gets its own bucket, exploding the row count.
  • Filtering cohorts before joining — a "cohorts with more than N signups" filter is a HAVING on the cohort-size aggregation, not a row filter on individual events.
  • Using LEFT JOIN backwards — the cohort table should drive the analysis; a user who never had an event gets a zero, not a missing row.

This is the multi-level pattern Practice Problem 4 below uses in miniature: a CTE with its own HAVING, joined into a second aggregation. Whenever a filter operates at a different grain than your final report — "big countries" vs. "country × category" — a single flat GROUP BY cannot express it; a CTE stack, one aggregation per level, can.

Practice Problems

1. COUNT(*), COUNT(status), and GROUP BY, with NULLs in the mix

Given orders(order_id, customer_id, total, status) with 100 rows total, 20 of which have status = NULL and 20 of which have total = NULL, what do these return?

(a) SELECT COUNT(*) FROM orders   (b) SELECT COUNT(status) FROM orders   (c) SELECT status, COUNT(*) FROM orders GROUP BY status   (d) SELECT AVG(total) FROM orders

▸ Reveal answer
  • (a) 100 — COUNT(*) counts every row.
  • (b) 80 — COUNT(status) skips NULLs: 100 − 20.
  • (c) One row per distinct status, plus one row for NULL. GROUP BY treats all NULLs as a single group — you'd see rows like ('pending', 30), ('shipped', 50), (NULL, 20), not 20 separate NULL rows.
  • (d) The sum of the 80 non-NULL totals divided by 80 — not divided by 100. This can silently shift a reported average whenever a lot of NULLs really mean "zero" rather than "missing."

2. Diagnose and rewrite

What's wrong with this query, and what are two valid fixes?

SELECT department, employee_name, COUNT(*) FROM employees GROUP BY department;
▸ Reveal answer

In standard SQL this fails: employee_name is neither in the GROUP BY nor wrapped in an aggregate, and each department has many names — SQL can't pick which one to show. (As the SQLite quirk above demonstrated, SQLite itself won't actually error here — it'll silently return one arbitrary name per department, which is its own kind of trap.)

Version A — count employees per department:

SELECT department, COUNT(*) AS employee_count FROM employees GROUP BY department;

Version B — list every employee with their department's count, without collapsing any rows:

SELECT department, employee_name, COUNT(*) OVER (PARTITION BY department) AS department_count FROM employees;

Version B uses a window function to attach a per-group aggregate to every row instead of collapsing them.

3. Both conditions are group-level

For sales(product_id, sale_date, sale_price), write a single query returning products where (a) at least 10 sales occurred, AND (b) the average sale price is above 25. Which clause holds each condition?

▸ Reveal answer

Both conditions are aggregate values, not individual-row values — both go in HAVING:

SELECT product_id, COUNT(*) AS n_sales, AVG(sale_price) AS avg_price FROM sales GROUP BY product_id HAVING COUNT(*) >= 10 AND AVG(sale_price) > 25;

WHERE cannot see COUNT(*) or AVG(sale_price). If you also needed to restrict to a specific year, that row-level filter would go in WHERE, before the GROUP BY:

... FROM sales WHERE sale_date >= '2026-01-01' -- row-level filter GROUP BY product_id HAVING ... -- group-level filter

4. Two aggregation levels in one query

Given sales(country, category, revenue), write a query that produces, for each country whose total revenue exceeds 1,000, a breakdown by category ordered by revenue descending within each country.

▸ Reveal answer

This needs two aggregation levels: aggregate first to test the country total, then aggregate again to break down by (country, category). A CTE keeps them cleanly separated:

WITH big_countries AS ( SELECT country FROM sales GROUP BY country HAVING SUM(revenue) > 1000 ) SELECT s.country, s.category, SUM(s.revenue) AS revenue FROM sales s JOIN big_countries bc ON bc.country = s.country GROUP BY s.country, s.category ORDER BY s.country, revenue DESC;

The HAVING inside the CTE filters countries; the outer query then aggregates the survivors by (country, category). A single flat GROUP BY can't express this — the "big country" test lives at a different aggregation level than the final report.

5. The COUNT(*) / COUNT(col) identity

If users has 500 rows and 300 have a non-null last_login, what do these return?

(a) SELECT COUNT(*) FROM users WHERE last_login IS NULL   (b) SELECT COUNT(last_login) FROM users

▸ Reveal answer
  • (a) 200 — the 500 − 300 = 200 rows where last_login IS NULL.
  • (b) 300 — COUNT on a column skips NULLs, so only the non-null rows count.

200 + 300 = 500 = total rows. The identity COUNT(*) = COUNT(col) + COUNT(*) WHERE col IS NULL always holds — the missing rows are counted somewhere, they just never count as a value.

Apply It

In the Interview

Aggregation shows up in every analytics-flavored SQL round and every product-metrics interview.

Product-analytics classic. "Given an events table, compute the 7-day rolling active users." The strong answer sketches COUNT(DISTINCT user_id) OVER (ORDER BY event_date RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW). Recognizing that a rolling metric is fundamentally a windowed aggregation — not a plain GROUP BY — instantly upgrades the conversation.

The "top-N per group" pattern. "Find the top 3 highest-paid employees in each department." A weak answer reaches for subqueries and LIMIT inside WHERE ... IN (...). The strong answer uses ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) and filters WHERE rn <= 3 in the outer query. This is one of the most-asked SQL interview problems on any leaderboard.

The "cohort analysis" pattern. "For each week of signup, what percentage of users were still active 4 weeks later?" Any senior data-engineering interviewer asks some variant. The four-step CTE walk-through above is the reference answer — sketch it on a whiteboard and you look like someone who has actually shipped analytics dashboards.

The gotcha interviewers use to filter candidates. "Given a feedback table where 30% of rows have NULL score, what does SELECT AVG(score) FROM feedback WHERE score >= 0 return, and what does SELECT AVG(score) FROM feedback return — are they the same?" The junior answer says yes without thinking. The correct answer: they're the same if all real scores are non-negative, because AVG(score) already ignores NULLs and WHERE score >= 0 is Unknown (dropped) for NULL rows — so both computations exclude exactly the same rows. A senior candidate then asks whether NULLs should count as zero for the business logic and, if so, wraps in COALESCE(score, 0) to change the answer.

Rule of thumb.

  • •Row-level filter → WHERE.
  • •Group-level filter (uses SUM/AVG/COUNT) → HAVING.
  • •Aggregation without collapsing rows → window function with OVER.
  • •Multi-level aggregation → CTE stack, one aggregation per level.

Any interviewer who asks "what would you use?" is testing whether you can pick the right tool without over-engineering.

2026 Status

In 2026: What Has Changed

GROUP BY is no longer the end of the story — it is the first rung of a ladder that ends at window functions.

  • GROUPING SETS, ROLLUP and CUBE produce several levels of summary — subtotals and grand totals — in a single pass.
  • FILTER (WHERE …) gives conditional aggregates (count of paid orders, average of refunded ones) without wrapping a CASE inside the aggregate.
  • Aggregation is the stepping stone to window functions: SUM(x) OVER (ORDER BY …) is the running total that GROUP BY cannot express.
  • Warehouse engines add approximations (approx_distinct, percentile_cont) that trade exactness for speed at scale.

GROUP BY collapses rows; window functions keep them. Knowing which one the question needs is the whole skill.
