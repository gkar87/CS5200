CTEs and Recursive Queries

Prepared by Dr. Gorkem Kar

Complex SQL usually starts as a simple query and then grows — a filter here, a join there, a subquery inside another subquery. Six months later it's 200 lines of nested parentheses that no one can safely change. Common Table Expressions are how you keep queries from rotting: instead of nesting logic inside logic, you name each step at the top and use those names below. The same syntax also unlocks something SQL used to be famously bad at — traversing hierarchies and graphs.

Foundations

Refactoring for Clarity

Common Table Expressions, or CTEs, change the way you build queries. Instead of nesting logic inside other logic, you define your building blocks at the top of the script and use them later. It turns a dense thicket of code into a linear story. Once you master this top-down approach, you can move into recursion, which lets SQL do something it usually struggles with: traversing hierarchies like org charts, file systems, and social networks.

Compare the same logic written two ways. First, as nested subqueries — you have to read from the inside out:

SELECT * FROM ( SELECT tc.customer_id, tc.total, p.category FROM ( SELECT customer_id, SUM(amount) AS total FROM sales GROUP BY customer_id ORDER BY total DESC LIMIT 100 ) AS tc JOIN products p ON p.customer_id = tc.customer_id ) AS enriched WHERE enriched.category = 'X';

Now the same thing as chained CTEs — reads top to bottom, one named step at a time:

WITH top_customers AS ( SELECT customer_id, SUM(amount) AS total FROM sales GROUP BY customer_id ORDER BY total DESC LIMIT 100 ), enriched AS ( SELECT tc.customer_id, tc.total, p.category FROM top_customers tc JOIN products p ON p.customer_id = tc.customer_id ) SELECT * FROM enriched WHERE category = 'X';
Nested subqueriesChained CTEs
Reading orderInside out (deep first)Top to bottom (natural)
DebuggingDig through parenthesesRun any CTE alone
ReuseCan't reference an inner subquery elsewhereAny earlier CTE is available to every later step
NamingAlias onlyNamed step per logical operation

Foundations

The WITH Clause

A standard subquery is a one-time-use tool. If you define a subquery in your FROM clause, you can only use it right there. If you need that same data again in a different part of the query, you have to copy and paste the entire block — bloated code, and more surface area for bugs to hide.

A CTE uses the WITH clause to name a result set you can reference throughout the rest of your query. Think of it like a variable that holds a table. Most people write queries that scatter the logic:

SELECT category, total_sales FROM ( SELECT category_id, SUM(price) as total_sales FROM orders GROUP BY category_id ) as sales_data JOIN categories ON sales_data.category_id = categories.id WHERE total_sales > (SELECT AVG(price) FROM orders);

You have to read the middle to find the data source, then look at the bottom for the filter. Here's the same logic refactored into named CTEs:

WITH CategorySales AS ( SELECT category_id, SUM(price) as total_sales FROM orders GROUP BY category_id ), AverageSale AS ( SELECT AVG(price) as avg_total FROM orders ) SELECT c.name, s.total_sales FROM CategorySales s JOIN categories c ON s.category_id = c.id CROSS JOIN AverageSale a WHERE s.total_sales > a.avg_total;

By pulling the logic to the top, you give it a name. Anyone reading this knows exactly what CategorySales represents without parsing the SUM and GROUP BY logic immediately. The final SELECT becomes a simple assembly of pre-built parts.

SQLite quirk — the original "scattered" query above has a real bug. Run the cell below and its first statement fails with no such column: category. The outer SELECT category, total_sales assumes a column named category exists, but the subquery only produces category_id, and the joined categories table has a column called name, not category — there's no column anywhere actually called category. It has to be written as categories.name AS category (or similar) to run at all. This is a good reminder that nested subqueries hide these mistakes in the middle of the query where they're easy to miss; the corrected nested version and the CTE version below both run cleanly and return identical rows once the alias is fixed.

Chained CTEs

The real power of this approach appears when you chain multiple CTEs together. Each CTE can reference the ones defined above it, letting you break a complex business problem into small, testable steps.

Suppose you need to find the top 5% of customers by revenue, then find which products those specific customers bought most often. Doing this in nested subqueries is a nightmare. Using chained CTEs, you define a TopCustomers block, then a CustomerProducts block that pulls from the first one, and finally a summary block. It reads like a recipe — one step prepares the ingredients, and the next step cooks them. (The full worked version of this exact report — top 5 customers, plus each one's top product — is built step by step later in Chained CTEs for a Real Report.)

A quirk worth knowing: an unreferenced CTE is dead code

If you define a CTE with WITH but never reference it anywhere in the rest of the query, what happens? In SQLite, nothing — it's simply never evaluated. It isn't even checked for a bad column reference, because the engine never has a reason to compile it. Don't rely on this to "hide" broken SQL on purpose — it's a sign the CTE is dead code and should probably be deleted, not a technique. But it explains why a leftover, half-finished CTE sometimes doesn't throw an error the way you'd expect.

Recursion

Anchor, Recursive, Union

Standard SQL is great at looking at rows side by side, but it's traditionally bad at looking at rows that relate to each other in a chain. If you have an employees table where each row has a manager_id, how do you find everyone who reports to the CEO, including the people who report to the people who report to the CEO?

A recursive CTE is the tool for this. It has a specific three-part structure:

  1. The Base Case (The Anchor). This is the starting point, like the CEO.
  2. The Recursive Case. This is the logic that finds the "next" level of data by joining the table back to the previous results.
  3. The Union. The UNION ALL command that stitches these layers together.

When you run a recursive query, the database doesn't just loop blindly. It follows a specific procedure: it executes the anchor query and puts those rows into a temporary "working table." Then it runs the recursive query using the contents of that working table. If it finds new rows, it replaces the working table with those new rows and does it again. It stops only when the recursive step returns zero new rows.

Tracing this org chart: Alice (ID 1) is the boss. Bob (ID 2) reports to Alice. Charlie (ID 3) reports to Bob.

WITH RECURSIVE org_chart AS ( -- Anchor: Find the CEO SELECT id, name, manager_id, 1 as level FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive: Find people who report to the previous level SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.id ) SELECT * FROM org_chart;

Step-by-step: Iteration 0 (Anchor) finds Alice, because her manager_id is NULL. The working table now contains Alice. Iteration 1 looks for anyone whose manager_id matches an ID in the working table (Alice's ID, 1) — it finds Bob, who's added to the results, and the working table is now updated to contain only Bob. Iteration 2 looks for anyone whose manager_id matches Bob's ID (2) — it finds Charlie, added to the results; working table now contains only Charlie. Iteration 3 looks for anyone whose manager_id matches Charlie's ID (3) — finds no one. The working table is empty. The process stops.

The final result is the union of all these iterations. If you forgot the anchor, the query would have nowhere to start. If you wrote the join logic incorrectly, it might never find the next level or, worse, it might find the same rows forever.

Graphs & Cycles

Graph Reachability and Cycles

Recursion isn't just for trees. It's also used for graphs, like a network of flights between cities. If you want to know whether you can get from New York to Singapore, a recursive CTE can explore every possible connection until it finds a path or runs out of options.

However, graphs introduce a danger that trees usually don't: cycles. If a flight goes from New York to London, and another goes from London back to New York, a naive recursive query will bounce between them forever. The database keeps finding "new" paths that are just the same cities in a circle.

flights origin destination NYC LON LON PAR LON NYC PAR ROM
WITH RECURSIVE reachable AS ( SELECT destination AS city FROM flights WHERE origin = 'NYC' UNION ALL SELECT f.destination FROM flights f JOIN reachable r ON f.origin = r.city ) SELECT DISTINCT city FROM reachable;

The recursive step keeps generating NYC → LON → NYC → LON → ..., producing infinite rows. Most DBMSes will error out after hitting an internal recursion limit (PostgreSQL: max_stack_depth; SQL Server: 32,767 by default) — or, worse, just hang. The cell below caps the naive version with LIMIT 12 so it's safe to run in your browser — without that cap, this query does not terminate on its own.

Notice the repeating LON / NYC / PAR pattern — that's the cycle bouncing forever, exactly as the article warns.

The fix: track where you've already been

To prevent this, you have to track where you have already been — by building a string or array of the path taken so far and checking whether the next city is already in that list. Most modern databases have safety limits to stop a runaway query, but a well-written query should handle its own termination logic.

WITH RECURSIVE reachable AS ( SELECT destination AS city, ARRAY['NYC', destination] AS path FROM flights WHERE origin = 'NYC' UNION ALL SELECT f.destination, r.path || f.destination FROM flights f JOIN reachable r ON f.origin = r.city WHERE NOT (f.destination = ANY(r.path)) -- cycle guard ) SELECT DISTINCT city FROM reachable;

The NOT (f.destination = ANY(r.path)) condition rejects any hop that would revisit a city already on the path. Different DBMSes have different array syntax (PostgreSQL uses ARRAY[] and ||; SQL Server uses string-based paths; MySQL 8+ supports JSON arrays; SQLite has no array type at all, so the cell below tracks the path as a delimited text string and uses instr() as the guard). The concept is identical everywhere: recursion over a cyclic graph requires explicit path tracking.

cycle_fixed_path_guard.sql
A subtlety worth noticing. The path-guarded version above returns exactly {LON, PAR, ROM} — it excludes NYC, because NYC is already in the starting path, so the guard blocks the LON→NYC hop from ever re-adding it. That's "cities strictly reachable without looping back to where you started."

Does plain UNION solve cycles for you?

UNION (as opposed to UNION ALL) deduplicates rows. In a recursive CTE with no path-tracking column, that can look like it "fixes" the cycle — SQLite's engine only keeps recursing on genuinely new rows, and once every reachable city has appeared once, the next iteration produces nothing new. Run the first query below: plain UNION, no path column, terminates cleanly and returns 4 cities — including NYC itself, since the cycle legitimately produces it once before dedup kicks in on further repeats. That's a different (also defensible) answer than the path-guarded version's 3 cities: it's "everywhere reachable, including a cycle back to the start" versus "everywhere reachable without revisiting the start."

But this "fix" is fragile. The moment you add a column that changes every iteration — like a hop counter — every row becomes unique again, so UNION's dedup can never kick in and the cycle runs forever exactly like UNION ALL would. The second query below adds a depth column and is capped with LIMIT 12 for safety; notice it keeps bouncing and growing depth forever, just like the naive UNION ALL version above.

union_dedup_vs_union_all.sql

Moral: don't rely on UNION's dedup as your cycle-termination strategy. It happens to work for the narrowest case (no extra columns) and breaks the instant you add one — use explicit path tracking instead, every time.

Worked Examples

Worked Example: Trace a Recursive Query Row-by-Row

Given this employees table (a different, slightly deeper hierarchy than the visualizer's above — here Frank reports to Dave, not Carol):

idnamemanager_id
1AliceNULL
2Bob1
3Carol1
4Dave2
5Eve2
6Frank4

Run this query and trace it iteration by iteration:

WITH RECURSIVE org AS ( SELECT id, name, manager_id, 1 AS depth FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.id, e.name, e.manager_id, o.depth + 1 FROM employees e JOIN org o ON e.manager_id = o.id ) SELECT * FROM org ORDER BY depth, id;
  • Iteration 0 (anchor): match manager_id IS NULL → {Alice, depth=1}. Working set: {Alice}. Result so far: {Alice}.
  • Iteration 1: join employees to working set on e.manager_id = o.id where o.id = 1 → matches Bob and Carol. New working set: {Bob depth=2, Carol depth=2}. Result cumulative: {Alice, Bob, Carol}.
  • Iteration 2: join with working set = {Bob(2), Carol(2)}. Bob's reports: Dave(4), Eve(5). Carol has no reports. New working set: {Dave depth=3, Eve depth=3}. Result cumulative: {Alice, Bob, Carol, Dave, Eve}.
  • Iteration 3: join with working set = {Dave(4), Eve(5)}. Dave's reports: Frank. Eve has none. New working set: {Frank depth=4}. Result cumulative: {Alice, Bob, Carol, Dave, Eve, Frank}.
  • Iteration 4: join with {Frank(6)}. No one reports to Frank. New working set: {}. Recursion terminates.

The termination condition — the recursive step returning zero new rows — is what stops the loop. In a cyclic graph, that never happens naturally, which is exactly why you must add explicit cycle detection (next section).

Worked Example: Chained CTEs for a Real Report

You want a business report: "top 5 customers by total revenue, and for each, list their most-purchased product." One giant nested query is unreadable; chained CTEs make it a pipeline:

WITH top_customers AS ( SELECT customer_id, SUM(total) AS revenue FROM orders GROUP BY customer_id ORDER BY revenue DESC LIMIT 5 ), customer_product_totals AS ( SELECT o.customer_id, ol.product_id, SUM(ol.quantity) AS qty FROM orders o JOIN order_lines ol USING (order_id) WHERE o.customer_id IN (SELECT customer_id FROM top_customers) GROUP BY o.customer_id, ol.product_id ), ranked AS ( SELECT customer_id, product_id, qty, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY qty DESC) AS rn FROM customer_product_totals ) SELECT tc.customer_id, tc.revenue, r.product_id AS top_product, r.qty FROM top_customers tc JOIN ranked r ON r.customer_id = tc.customer_id AND r.rn = 1 ORDER BY tc.revenue DESC;

Four named building blocks, each answering one small question:

  • top_customers — who are the top 5 by revenue?
  • customer_product_totals — how many units did each of them buy of each product?
  • ranked — order those products by quantity within each customer.
  • Main SELECT — glue the top product per customer to their revenue.

You could inline every CTE as a nested subquery, but the resulting query would be 5+ levels deep and much harder to review. CTEs are the SQL equivalent of extract-method refactoring.

Practice Problems

1. Refactor a nested query into two CTEs

Take this deeply-nested query and refactor it using two CTEs:

SELECT dept, avg_salary FROM ( SELECT dept, AVG(salary) AS avg_salary FROM employees WHERE hire_date >= '2022-01-01' GROUP BY dept ) e WHERE e.avg_salary > (SELECT AVG(salary) FROM employees);
▸ Reveal answer

Name the inner aggregate and the overall average as two separate CTEs, then compare them in the final SELECT:

WITH dept_avg_recent AS ( SELECT dept, AVG(salary) AS avg_salary FROM employees WHERE hire_date >= '2022-01-01' GROUP BY dept ), overall_avg AS ( SELECT AVG(salary) AS avg_salary FROM employees ) SELECT d.dept, d.avg_salary FROM dept_avg_recent d CROSS JOIN overall_avg o WHERE d.avg_salary > o.avg_salary;

Verified against real SQLite: both the original nested version and this refactor return the identical row for a sample dataset (Eng, 92500). The CTE version just makes each half of the comparison a nameable, independently-runnable step.

2. Trace a recursive CTE by hand

Trace this recursive CTE by hand for the given parts table. What is the final result?

CREATE TABLE parts (assembly VARCHAR, part VARCHAR); INSERT INTO parts VALUES ('bike', 'frame'), ('bike', 'wheel'), ('wheel', 'spoke'), ('wheel', 'rim'), ('frame', 'tube'), ('tube', 'metal');
WITH RECURSIVE bom AS ( SELECT assembly, part, 1 AS depth FROM parts WHERE assembly = 'bike' UNION ALL SELECT p.assembly, p.part, b.depth + 1 FROM parts p JOIN bom b ON p.assembly = b.part ) SELECT * FROM bom ORDER BY depth, part;
▸ Reveal answer

The anchor starts at bike (depth 1: frame, wheel). Each iteration looks for parts whose assembly matches a part just found — wheel and frame are themselves assemblies of smaller parts, so the recursion continues one more level, then tube is itself an assembly of metal for a third level:

depthassemblypart
1bikeframe
1bikewheel
2frametube
2wheelrim
2wheelspoke
3tubemetal

Verified against real SQLite: this exact 6-row result comes back, ordered by depth then part. This is a real bill-of-materials (BOM) pattern — the same shape a manufacturing system uses to cost out an assembly recursively.

3. UNION vs. UNION ALL in a recursive CTE

Explain what happens when you replace UNION ALL with UNION in a recursive CTE. Give one case where it matters.

▸ Reveal answer

UNION deduplicates rows between the anchor and every recursive step; UNION ALL keeps every row, duplicates included. For tree-shaped data (no cycles, and no reason the same exact row would ever recur), the two behave identically — UNION ALL is preferred because it's cheaper (no dedup comparison every iteration).

Where it matters: on a cyclic graph with no extra per-row columns (see the Reachability and Cycles section above), UNION's deduplication can accidentally make a naive query terminate, because once every reachable node has appeared, the next iteration produces only rows the engine has already seen and dedupes away — zero new rows, so it stops. UNION ALL on that same query loops forever. But this is a fragile accident, not a real fix: the moment the recursive step carries a column that changes every iteration (a depth counter, an accumulated path), every row is unique again, dedup can never trigger, and UNION loops forever too — verified live in the cell above. Always use explicit path-tracking for real cycle safety; never rely on plain UNION's dedup as the termination strategy.

4. Friends within 3 hops, with cycles

You have friends(person_id, friend_id) representing a social graph. Write a recursive CTE that returns everyone within 3 hops of person 1 (including person 1). Handle cycles.

▸ Reveal answer
WITH RECURSIVE network AS ( SELECT 1 AS person_id, 0 AS hops, '|1|' AS path UNION ALL SELECT f.friend_id, n.hops + 1, n.path || f.friend_id || '|' FROM friends f JOIN network n ON f.person_id = n.person_id WHERE n.hops < 3 AND instr(n.path, '|' || f.friend_id || '|') = 0 -- cycle guard ) SELECT DISTINCT person_id FROM network ORDER BY person_id;

Two safety mechanisms working together: WHERE n.hops < 3 bounds the depth (so it can never recurse past 3 hops even without a cycle), and the instr(...) path check stops it from ever re-visiting a person already on the current path — necessary because friends can easily contain a cycle (person A → B → C → A). Verified against real SQLite with a graph that includes exactly such a cycle: the query returns cleanly rather than hanging.

5. An unused CTE among four

A colleague writes a query with 4 separately-defined CTEs (WITH a AS (...), b AS (...), c AS (...), d AS (...)) where d references only a and b, and c isn't used anywhere. What happens at execution time? Is this a bug?

▸ Reveal answer

In every mainstream engine, c is simply never executed — a CTE is only materialized (or inlined) if something downstream actually references it. It costs nothing at runtime.

Verified against real SQLite in the Chained CTEs section above: a CTE c that references a genuinely nonexistent column doesn't even throw a compile error, because the engine never binds or validates a CTE it has no reason to run. It's not a runtime bug — but it's very likely a maintenance bug: dead, unreferenced SQL that a future reader will assume matters and waste time trying to understand, or that silently goes stale as the schema changes underneath it. Delete unused CTEs the same way you'd delete unused variables.

Apply It

In the Interview

CTEs and recursive queries show up in senior SQL rounds and in system-design conversations where hierarchies come up.

The readability round. A senior candidate is shown a 60-line SQL query with three levels of nested subqueries and asked "how would you refactor this?" The expected answer is "extract the intermediate results into CTEs, one per logical step" — the SQL equivalent of extract-method. Bonus points for mentioning that in older PostgreSQL, CTEs were an optimization fence, so refactoring to CTEs could change performance and you should benchmark. In current PostgreSQL and every major DBMS, CTEs are inlined by default unless marked MATERIALIZED.

The graph-and-hierarchy question. "Given an employees table with a manager_id, list every subordinate under a specific manager and their depth." This is a canonical recursive CTE question. Interviewers watch for four things:

  • 1.Anchor member clearly identifies the starting row (WHERE emp_id = ? or manager_id IS NULL).
  • 2.Recursive member joins the CTE back to the base table on the correct FK.
  • 3.UNION ALL (not UNION) — the latter is more expensive without changing semantics for tree data.
  • 4.Termination condition is implicit but must be understood — recursion ends when no new rows are produced. If the interviewer follows up "what if the manager graph has a cycle?", the answer is a visited array or path column plus a not-equal / not-in check.

A common interview trap. "Can you compute a running total with a plain CTE?" No — running totals require ORDER BY across rows, which is a window-function concept. Recognizing that CTEs and window functions solve different problems (CTEs give queries structure; window functions compute across rows) is worth pointing out even when not asked.

The GraphQL / API design tie-in. "Your GraphQL API needs to return a user, their friends, and their friends' friends. Two SQL queries or one?" The right answer is often one recursive CTE with depth ≤ 2. Modern APIs increasingly rely on this pattern because the alternative — N+1 queries from application code — is what caused Facebook to invent GraphQL in the first place.

Rule of thumb.

  • •Deeply nested subqueries hurting readability → chained (non-recursive) CTEs.
  • •"Walk up/down" a hierarchy, unbounded depth → recursive CTE.
  • •Traversing a graph that may contain cycles → recursive CTE + explicit path tracking.
  • •Aggregating across rows without collapsing them → window function, not a CTE.

Whenever a question involves "walk up/down" a hierarchy, "trace reachability" through a graph, or "compute across levels of aggregation," reach for a CTE — recursive if the depth is unbounded, chained if you have a linear pipeline of steps.

2026 Status

In 2026: What Has Changed

CTEs stopped being syntax sugar and became the standard way relational engines express graphs.

  • MATERIALIZED / NOT MATERIALIZED hints let you choose whether a CTE is an optimisation fence or is inlined into the query that uses it.
  • Recursive CTEs are how relational engines do graphs — org charts, bills of materials, dependency order, and shortest paths with a depth column.
  • SQL:2023 added SEARCH and CYCLE clauses, so depth-first/breadth-first ordering and cycle detection are declarative instead of hand-rolled.
  • The failure mode is an infinite loop, so a depth limit or a cycle test belongs in the query itself rather than in a bug report later.

Recursion is the part of SQL that surprises people who assume SQL cannot express iteration.
