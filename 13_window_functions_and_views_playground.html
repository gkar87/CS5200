Window Functions and Views

Prepared by Dr. Gorkem Kar

For most of this course, an aggregate has meant a collapsed answer: ask for a total, and the rows you started with are gone. But a huge class of real questions needs both at once — every row, and a value computed over a group of rows. Window functions answer exactly that. And a view answers a different recurring need: giving many callers one stable, named query instead of asking each of them to reconstruct it. Together they are the last two pieces of the SQL you will write by hand.

Foundations

Windows Preserve Rows; GROUP BY Collapses Them

Every aggregate you have written so far — SUM, COUNT, AVG — went with a GROUP BY, and GROUP BY does exactly one thing: it collapses each group of rows into a single output row. Ask for the total revenue per region and you get one row per region. The individual sales are gone.

That collapse is often the right answer, but sometimes you need to keep the detail and attach a group-level value to it. "Show each sale, and next to it the total for that sale's region" is impossible with a plain GROUP BY without a join back to a grouped subquery. A window function does it directly: it computes across a set of related rows while leaving every original row in place.

Foundations

The OVER Clause

A window function is written like an aggregate with a suffix. SUM(amount) is an aggregate; SUM(amount) OVER (...) is a window function. The word OVER is what turns one into the other, and everything inside the parentheses describes which rows the function is allowed to see.

The OVER clause has three independent parts, and the third is the one people forget:

ClauseWhat it doesExample
PARTITION BYSplits the table into independent groups. The function restarts for each group.PARTITION BY region
ORDER BYOrders rows within each partition — this is what makes running totals and ranks possible.ORDER BY sale_date
FrameNarrows the window to a slice relative to the current row, e.g. the last three rows.ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
Order of evaluation. Window functions are computed after WHERE and GROUP BY, but before the final ORDER BY. That single fact explains why you cannot put a window function in a WHERE clause — the value does not exist yet when WHERE runs.

An empty OVER () means "the whole result set": every row sees every other row. Adding ORDER BY turns the window from "all rows" into "all rows up to and including the current one." Adding PARTITION BY resets that accumulation for each group.

Windows

Running Totals

The canonical first window function is a running total. Remove PARTITION BY and keep only an ORDER BY inside the OVER, and the frame defaults to "from the start of the partition up to the current row." Each row therefore sees itself and everything ordered before it — and summing that gives a running total.

Now add PARTITION BY department inside the OVER. The running total resets at the first row of each department and starts climbing again — because a partition is an independent window, not a continued one.

Windows

Ranking: ROW_NUMBER, RANK, and DENSE_RANK

Three window functions produce ranks, and the only thing that separates them is how they treat a tie. Given the same ORDER BY:

  • ROW_NUMBER() always produces a unique sequence: 1, 2, 3, 4, 5. Ties are broken arbitrarily, so it is not stable unless you add a tie-breaker column.
  • RANK() gives tied rows the same rank and then skips the ranks it used up, leaving a gap.
  • DENSE_RANK() gives tied rows the same rank and does not skip — the next distinct value gets the very next rank.

With scores 100, 100, 90, 80, 80 the three columns read: ROW_NUMBER gives 1,2,3,4,5; RANK gives 1,1,3,4,4; DENSE_RANK gives 1,1,2,3,3. "Same rank, skip" versus "same rank, do not skip" is the whole specification.

Windows

ROWS vs. RANGE: What a Frame Includes

When you add ORDER BY to a window, the frame no longer means "all preceding rows" in a simple positional sense — it becomes a choice between counting physical rows and counting peers. ROWS walks row by row. RANGE treats every row with the same ORDER BY value as one unit, and includes all of them together.

rows_vs_range.sql — edit and run

Both columns end at the same total (455), but they disagree in the middle: on a day with two rows, ROWS adds only the first of them, while RANGE has already absorbed the whole tied day. The default when you write ORDER BY alone is RANGE UNBOUNDED PRECEDING, which is why running totals on tied dates surprise people.

Windows

LAG and LEAD: Comparing to Neighbours

Not every window function is an aggregate. LAG and LEAD reach into the window and return the value from the previous or next row. They turn "compare each day to the day before" from a self-join into a single clause — and the first row's LAG is simply NULL, because there is no row before it.

lag_lead.sql — edit and run

Both accept an optional offset and default: LAG(price, 1, 0) would replace that leading NULL with 0. Choosing an explicit default is often clearer than letting the first row come back empty.

Composing a Pipeline

Real analytics queries compose several window functions in one pass over a CTE. The recurring shape is a four-beat pattern you can apply to almost any question: partition → order → compute → filter.

  1. Partition — decide what "a group" means in this question (region, customer, day).
  2. Order — decide what "before" means within the group (by date, by amount).
  3. Compute — stack the window functions you need: a running total, a rank, a neighbour comparison.
  4. Filter — wrap the result in a CTE or subquery and keep only the rows you actually want.

Views

Views: Reusable Data Interfaces

A view is a named, stored query. You write CREATE VIEW name AS SELECT ... once, and from then on every caller can treat name like a table: SELECT * FROM name. The view stores no rows of its own — when you query it, the database runs its definition and hands you the result.

The reason views matter is not convenience, it is consistency of access. If five reports each hand-write the same complicated filter, a change to the rule has to be applied in five places, and someone will miss one. Put the rule in a view, and every report reads the same definition. Restrict which columns a role can see, and the view becomes a permission boundary as well as a convenience.

view_interface.sql — edit and run

There is a second reason views appear in real schemas: compatibility. When a table is restructured, a view with the old shape can sit in front of the new tables, and applications that only ever read the view keep working. The view absorbs the change.

Views

The View Boundary: When a Row Vanishes

Because a view is defined by a WHERE clause, a row can be visible through the view at one moment and gone from it the next — even though nothing was deleted. If the underlying row stops satisfying the view's predicate, it simply drops out of the view's result. Watch it happen.

view_boundary.sql — edit and run

The view's WHERE clause is a filter, not a boundary. Standard SQL gives you a way to make it a boundary: WITH CHECK OPTION. When a view is updatable and declared with WITH CHECK OPTION, the database refuses any write that would push a row out of the view's predicate. The rule becomes an integrity constraint in its own right.

Engine note. SQLite (and therefore the in-browser engine here) does not implement auto-updatable views or WITH CHECK OPTION; a SQLite view is read-only unless you attach an INSTEAD OF trigger. PostgreSQL, MySQL, and Oracle do support both, and this is where the feature is normally taught:
CREATE VIEW cheap_products AS SELECT id, name, price FROM products WHERE price < 100 WITH CHECK OPTION; -- PostgreSQL: rejects any update that breaks price < 100

The idea transfers regardless of engine: a view is an access rule, and WITH CHECK OPTION is how standard SQL lets you enforce that rule on writes as well as reads.

Worked Examples

Worked Example: Preserve or Collapse?

A marketing team wants a report of daily sales. They also want each row to show what fraction of that day's total it represents. A grouped aggregate seems natural:

SELECT day, SUM(amount) AS day_total FROM Sales GROUP BY day;

This gives one row per day — but the individual sales are gone, so there is no "each row" left to show a fraction of. The question conflates two different outputs. The window version keeps the detail:

SELECT day, amount, SUM(amount) OVER (PARTITION BY day) AS day_total, ROUND(amount * 100.0 / SUM(amount) OVER (PARTITION BY day), 1) AS pct FROM Sales;

Both queries are correct — they answer different questions. The habit to build is this: before you write an aggregate, ask whether the answer should replace the rows or annotate them. Replace means GROUP BY; annotate means OVER.

A tempting middle path is GROUP BY followed by a join back to the base table. It works, but it scans the data twice and buries the intent. The window version says what it means in one pass.

Worked Example: Choosing a Ranking Function

A scholarship committee will award exactly three grants to the three highest scorers. Six students apply; two of them tie for second place. The choice of ranking function now decides who gets the third grant.

StudentScoreROW_NUMBERRANKDENSE_RANK
Ana98111
Ben95222
Cleo95322
Dai91443
Eve88554
Fay88654

Filtering each to the top three tells three different stories:

  • ROW_NUMBER() <= 3 returns Ana, Ben, and Cleo — it silently picks one of the tied pair and drops the other, which is unfair unless a documented tie-breaker exists.
  • RANK() <= 3 also returns three students, but only because the gap lands after Cleo. Change the scores slightly and it could return two or return four.
  • DENSE_RANK() <= 3 returns four students (Ana, Ben, Cleo, Dai) — it treats "three distinct scores" as the target, not "three students."

The lesson is not that one function is right. It is that "out of six applicants pick the three best" is under-specified when there are ties, and the ranking function is where you make the tie policy explicit.

Apply It

Practice Problems

1. Rank without collapsing

Given Employee(eid, name, dept, salary), write one query that returns every employee together with their salary rank inside their own department (highest salary = rank 1), keeping all employees in the output.

▸ Reveal answer
SELECT eid, name, dept, salary, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS dept_rank FROM Employee;

PARTITION BY dept restarts the ranking for each department; ORDER BY salary DESC makes the highest salary rank 1. Every employee row survives because a window function annotates rather than collapses. If you wanted strictly one row per salary value you would use DENSE_RANK instead.

2. Why did this query fail?

A developer writes:

SELECT name, salary FROM Employee WHERE RANK() OVER (ORDER BY salary DESC) <= 10;

Explain the error and give the corrected query.

▸ Reveal answer

Window functions are evaluated after the WHERE clause, so at the moment WHERE runs the rank does not exist yet. The engine rejects the reference. Compute the rank one level down and filter the outer query:

SELECT name, salary FROM ( SELECT name, salary, RANK() OVER (ORDER BY salary DESC) AS rk FROM Employee ) WHERE rk <= 10;

This "compute in a subquery or CTE, filter outside" shape is the standard workaround and the reason the four-beat pipeline ends with a filter.

3. Running total or region total?

Given Sales(region, sale_date, amount), write (a) a running total per region over time, and (b) one row per sale showing the region's grand total. What is the difference in the OVER clause?

▸ Reveal answer
-- (a) running total per region SELECT region, sale_date, amount, SUM(amount) OVER (PARTITION BY region ORDER BY sale_date) AS running FROM Sales; -- (b) region grand total beside each sale SELECT region, sale_date, amount, SUM(amount) OVER (PARTITION BY region) AS region_total FROM Sales;

The only difference is the ORDER BY inside the window. Without it, the frame is the whole partition, so you get the grand total. With it, the frame grows row by row, so you get a running total. Same function, same partition, different frame.

4. When is a view the right tool?

You support three internal reports that all filter to the same subset of a large Orders table. A colleague suggests copying the filtered rows into a new table refreshed nightly. Give two reasons a view is preferable.

▸ Reveal answer
  • Always current. A view re-runs its definition on every read, so it never serves stale data; a nightly copy is wrong for up to twenty-four hours.
  • One definition of the rule. Change the filter in the view and all three reports change together; a copied table means three silent copies of the rule and a data-redundancy problem of exactly the kind this course opened with.

A materialised view is the honest middle ground when performance genuinely demands a stored copy — but that is a caching decision on top of the logical view, not a replacement for it.

Apply It

In the Interview

Window functions are one of the clearest senior/junior signals in a SQL interview. A candidate who reaches for a self-join where a window would do, or who cannot explain why a window cannot go in WHERE, is usually not yet comfortable with the execution model.

"What's the difference between GROUP BY and a window function?" The strong answer is about rows: GROUP BY collapses each group to one row, while a window function computes across a set of related rows and keeps every row. Then name the win: a window avoids the join-back-to-a-grouped-subquery pattern that grouped aggregates otherwise require.

"ROW_NUMBER, RANK, or DENSE_RANK?" Recite the tie behaviour, not just the names: ROW_NUMBER is unique and arbitrary on ties; RANK ties then skips; DENSE_RANK ties then does not skip. Then connect it to a requirement — "for a strict top-N I would use ROW_NUMBER with an explicit tie-breaker, because the business asked for exactly N rows."

"Why can't I use a window function in WHERE?" Because of evaluation order: WHERE runs before window functions are computed. The fix is a CTE or subquery that computes the window, filtered by the outer query. Being able to state the logical order — FROM → WHERE → GROUP BY → window → ORDER BY → LIMIT — is the mark of someone who has actually used these.

"What is a view for?" Say plainly: a saved query that gives many callers one consistent access path — simplifying a complex rule, restricting columns or rows for a role, or preserving a stable interface while the underlying tables change. If asked about writes, mention that simple views are updatable in standard SQL and WITH CHECK OPTION turns the view's predicate into a write-time constraint.

Rule of thumb.

  • •Ask "do I want the rows replaced or annotated?" before choosing between GROUP BY and OVER.
  • •When ties exist, the ranking function is the tie policy — make it explicit.
  • •A view is a named query you can reason about like a table; WITH CHECK OPTION is what makes it a boundary you can trust on writes.
2026 Status

The Modern Database Landscape

Window functions and views were standardised decades ago, and they have only become more central as analytics moved into the operational database. Where a company once copied data into a separate warehouse before it could compute a running total, most stack decisions in 2026 assume analytical SQL — window functions, CTEs, and views — runs directly against the same tables the application writes to.

  • Analytical SQL everywhere. PostgreSQL, MySQL 9, SQL Server, Oracle, DuckDB, Snowflake, and BigQuery all implement the core window functions in this lecture. The clause syntax you learned here is portable across the entire industry.
  • Materialised views and "live" tables. Managed platforms (PostgreSQL, Snowflake, BigQuery, and the managed Postgres behind most serverless stacks) let a view be materialised and incrementally refreshed, so the same definition serves both correctness and performance.
  • Views as an API boundary. PostgREST, Supabase, Hasura, and similar tools expose database views as HTTP endpoints directly, which makes "a view is a stable interface" a literal product feature rather than a metaphor.
  • AI-generated SQL raises the stakes. An assistant will happily write a window function for you — and just as happily put it in a WHERE clause. Knowing the evaluation order is what lets you read the generated query and catch the mistake before it reaches production.

The two ideas in this lecture are the last hand-written pieces of SQL in the course: windows let you compute across related rows without losing them, and views let you name a query once and trust every caller to use it consistently. Everything after this — transactions, indexing, physical design — assumes you are fluent in both.
