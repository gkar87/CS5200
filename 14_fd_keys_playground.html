Functional Dependencies and Keys

Prepared by Dr. Gorkem Kar

Behind every well-designed schema is a small set of mathematical facts nobody thinks about until something breaks. "If I know a student ID, I know exactly one name." These are functional dependencies — the rules that say which attributes determine which. They look pedantic on paper. They are the reason normalization can be done by algorithm instead of by intuition. Once you can read them fluently, you can look at a schema and predict which updates will corrupt it, which queries will need redundant joins, and which tables should be split.

Foundations

The Core Concept: Functional Dependencies

A functional dependency (FD) is a relationship between two sets of attributes in a database. If you have a set of attributes X and another set Y, we say that X functionally determines Y if every value of X is associated with exactly one value of Y. We write this as X → Y.

Think of a Social Security Number. If you know a person's SSN, you know their legal name — there is no scenario where one SSN maps to two different people. Therefore, SSN → Name. The opposite is not true: multiple people can be named "John Smith," so Name → SSN does not hold. In this relationship, X is the determinant — it's the piece of information that gives you the power to look up something else.

The left panel above obeys StudentID → Name: S101 always maps to Alice, no matter how many rows reference S101. The right panel breaks it — S101 maps to both "Alice" and "Charlie" in different rows, which is a contradiction, not just messy data. Enforcing FDs (through primary keys, unique constraints, and correct table design) is precisely what makes that right-hand scenario structurally impossible rather than just unlikely.

Armstrong's Axioms: The Rules of Inference

In 1974, William Armstrong defined a set of rules that let us discover new dependencies from the ones we already know. You only need three basic rules to derive every other possible dependency in a system.

Reflexivity

If Y is a subset of X, then X → Y. For example, if you know a person's name and their birthday, you obviously know their name. Written as {Name, Birthday} → Name. It seems obvious, but it's the logical foundation for everything else.

Augmentation

If X → Y is true, then adding another attribute Z to both sides remains true. If SSN → Name, then it's also true that {SSN, ZipCode} → {Name, ZipCode}. You haven't lost any information by adding more context.

Transitivity

This is the most useful rule for finding hidden relationships. If X → Y and Y → Z, then X → Z. If a student ID determines a major code (ID → MajorCode) and the major code determines the department head (MajorCode → DeptHead), then the student ID effectively determines the department head: ID → DeptHead.

Derived rules

Beyond these three, we often use derived rules to speed up our work:

  • Union. If X → Y and X → Z, then X → YZ.
  • Decomposition. If X → YZ, then X → Y and X → Z.
  • Pseudo-transitivity. If X → Y and WY → Z, then WX → Z.

Every one of these derived rules is provable from the three basic axioms alone — they're conveniences, not new assumptions. The Practice Problems section below works through a full derivation using them.

Computing Attribute Closure

The closure of a set of attributes X, written X⁺, is every attribute you can derive from X using the functional dependencies you have. The algorithm treats it as a growing set: start with X, and repeatedly apply any FD whose left-hand side is already inside the set, adding whatever's on the right-hand side that isn't already there. Stop when nothing new can be added.

Given FDs A → B, B → C, C → D, here's {A}⁺ step by step:

StepWorking setFD appliedResult
0{A}(start with input)initial state
1{A}A → B — LHS is in the setadd B → {A, B}
2{A, B}B → C — LHS is in the setadd C → {A, B, C}
3{A, B, C}C → D — LHS is in the setadd D → {A, B, C, D}
4{A, B, C, D}(no unused FD applies)STOP

Conclusion: {A}⁺ = {A, B, C, D} — since the closure equals every attribute of the relation, A alone is a superkey. The algorithm always terminates: each step either grows the set by at least one attribute or stops, so in the worst case it terminates in |attributes| steps. Finding Candidate Keys

A candidate key is a minimal set of attributes that can uniquely identify every row in a table. Formally, a set of attributes K is a candidate key if two things are true:

  • The closure of K includes every attribute in the table.
  • No subset of K can do the same thing.

To find candidate keys, look for attributes that never appear on the right side of any functional dependency. These attributes must be part of your key, because nothing else can "create" them. If the closure of these must-have attributes doesn't cover the whole table, you start adding other attributes one by one until you reach a full closure.

If you find that {A, B}⁺ covers the whole table, but {A}⁺ and {B}⁺ do not, then {A, B} is a candidate key. If you could remove B and still get everything, {A, B} would be a superkey, but not a candidate key. Candidate keys must be lean.

The point isn't that email happens to be unique in your sample — it's that nothing in the schema said so. A candidate key you have discovered is worth nothing until the engine enforces it.

Foundations

The Minimal Cover

A set of functional dependencies can often be messy — redundant rules, or rules with extra attributes that don't need to be there. A minimal cover is the most stripped-down, efficient version of your rule set that still describes exactly the same relationships.

Finding the minimal cover is three specific steps:

First, ensure every dependency has only one attribute on the right side. A → BC becomes A → B and A → C. This makes the rules easier to inspect.

Second, remove extraneous attributes from the left side. If you have AB → C, check whether A → C is already true on its own, using the other rules. If it is, B is extraneous and can be deleted — the rule simplifies to A → C.

Third, remove redundant dependencies. For each rule, ask: "if I deleted this rule, could I still figure it out using the other rules?" If you have A → B, B → C, and A → C, the rule A → C is redundant because transitivity already covers it.

Worked Examples

Worked Example: Computing Attribute Closure Systematically

Given the relation R(A, B, C, D, E) with functional dependencies:

  • A → BC
  • B → D
  • CD → E
  • E → A

Compute A⁺ step by step. Iteration 0: start with {A}. Iteration 1: which FDs have their entire left-hand side inside {A}? A → BC — yes. Add B and C. Set = {A, B, C}. Iteration 2: which FDs have LHS inside {A, B, C}? B → D — yes, add D → {A, B, C, D}. CD → E — LHS {C, D} both present, add E → {A, B, C, D, E}. Iteration 3: set is the full relation. Stop. A⁺ = {A, B, C, D, E}.

Because A⁺ covers every attribute in R, {A} is a superkey. It's also minimal (a single attribute — you can't remove anything). Therefore {A} is a candidate key. Now compute E⁺: {E} → E → A applies → {E, A} → now that A is in the set, A → BC applies → {E, A, B, C} → B → D applies → {E, A, B, C, D}. Full. So {E} is also a candidate key.

What about {B, C}? Continuing this way: is {B, C} a candidate key? Compute {B, C}⁺ below and see for yourself, then check the two single-attribute subsets. The short answer: {B, C}⁺ genuinely does close over everything (via B → D, then CD → E, then E → A) — and since neither {B} alone nor {C} alone gets there, {B, C} is minimal. {B, C} is a candidate key. (This schema turns out to have three candidate keys total: {A}, {E}, and {B, C}.)

Worked Examples

Worked Example: Finding All Candidate Keys

Given R(A, B, C, D, E, F) with FDs AB → C, C → D, D → E, AF → B:

Step 1 — identify attributes that appear ONLY on the LHS (never on the RHS of any FD). Those must be in every candidate key. Scanning: A appears only on LHS. F appears only on LHS. B, C, D, E each appear on both sides. So A and F must be in every candidate key.

Step 2 — compute {A, F}⁺: start {A, F} → AF → B applies, add B → {A, F, B} → now AB → C applies (both present), add C → {A, F, B, C} → C → D applies, add D → {A, F, B, C, D} → D → E applies, add E → {A, F, B, C, D, E}. Full.

So {A, F} covers everything, and it's minimal — dropping either A or F would exclude an attribute nothing else on the RHS can produce. {A, F} is the unique candidate key. There are no others: any candidate key must contain {A, F}, and {A, F} alone already closes the relation.

Worked Examples

Worked Example: Computing a Minimal Cover Step by Step

Given FDs on R(A, B, C, D): A → B, AB → C, D → AC, C → D.

Step 1 — Singleton RHS. Decompose D → AC into D → A and D → C. Now F is: A → B, AB → C, D → A, D → C, C → D.

Step 2 — Remove extraneous LHS attributes. Consider AB → C. Is B extraneous? Compute A⁺ under the original F: A → B gives B for free, and then AB → C applies (both A and B present), giving C too — so A⁺ already includes C without needing B on the left. B is extraneous. Rewrite as A → C. F now: A → B, A → C, D → A, D → C, C → D.

Step 3 — Remove redundant FDs. For each FD, temporarily remove it and check whether it still follows from the rest:

  • Remove A → B: closure of A under the remaining set = {A, C, D} (via A→C→D). Doesn't include B. Essential.
  • Remove A → C: closure of A = {A, B}. No C. Essential.
  • Remove D → A: closure of D under {A→B, A→C, D→C, C→D} = {D, C}. No A. Essential.
  • Remove D → C: closure of D under the remaining = {D, A, B, C} (via D→A→C). Redundant — remove it.
  • Remove C → D: closure of C = {C}. Nothing else. Essential.

Minimal cover = { A → B, A → C, D → A, C → D }.

Practice Problems

1. Compute B⁺ and test candidacy

Given R(A, B, C, D) with FDs { A → B, B → C, C → D, D → A }, compute B⁺ and determine whether B is a candidate key.

▸ Reveal answer

B⁺: Start {B}. B → C → add C. {B, C}. C → D → add D. {B, C, D}. D → A → add A. {B, C, D, A}. Full.

B⁺ covers all attributes, so B is a superkey. Since it's a single attribute (minimal), it's a candidate key.

By the same argument, {A}, {C}, and {D} are all candidate keys too — the FDs form a cycle A→B→C→D→A. This schema has four single-attribute candidate keys, an unusual property that makes it BCNF-compliant automatically (every FD's LHS is a superkey).

2. Superkey vs. candidate key

Given R(A, B, C) with FDs { AB → C, A → B }, are {A, B} and {A} both candidate keys? Justify.

▸ Reveal answer

Compute A⁺: start {A}. A → B applies, add B: {A, B}. AB → C applies (both present), add C: {A, B, C}. Full. So A⁺ = {A, B, C} — A alone is a superkey, and minimal, so A is a candidate key.

{A, B}⁺ closes over everything too, but it's not minimal — we can drop B (since A alone works). So {A, B} is a superkey, but not a candidate key.

The rule: a candidate key must be minimal. Any superset of a candidate key is a superkey but not a candidate key.

3. Prove AD → BCEF with Armstrong's derived rules

Given FDs { A → BC, D → E, AD → F }, apply Armstrong's derived rules to prove AD → BCEF.

▸ Reveal answer
  1. A → BC. (given)
  2. AD → BCD (augmentation of #1 with D on both sides).
  3. AD → BC (decomposition of #2 — we don't need D on the RHS).
  4. D → E. (given)
  5. AD → AE (augmentation of #4 with A on both sides), then by decomposition, AD → E.
  6. AD → F. (given)
  7. Combine using the union rule: AD → BC (step 3), AD → E (step 5), AD → F (step 6) → AD → BCEF.

The union rule (X → Y and X → Z ⟹ X → YZ) is a shortcut for what would otherwise be several augmentation + decomposition steps. Verified directly too: computing {A, D}⁺ from these three FDs closes to {A, B, C, D, E, F} in one pass — matching the derivation.

4. Is AC → E redundant?

Given R(A, B, C, D, E) with FDs { A → B, BC → D, D → E, AC → E }, is AC → E redundant?

▸ Reveal answer

Test: can we derive AC → E from the other three FDs alone? Compute {A, C}⁺ using only { A → B, BC → D, D → E }: start {A, C}. A → B applies, add B: {A, C, B}. BC → D applies (both B and C in the set), add D: {A, C, B, D}. D → E applies, add E: {A, C, B, D, E}. Full.

Since {A, C}⁺ under the reduced set already includes E, we can derive AC → E from the others. AC → E is redundant and can be removed from a minimal cover.

5. Does this minimal cover entail these FDs?

You're told R(A, B, C, D) has minimal cover { A → B, B → C, C → D }. Are the following FDs entailed by this cover?

(a) A → D   (b) B → A   (c) D → A   (d) AD → BC   (e) B → BD

▸ Reveal answer
  • (a) Yes. A → B → C → D by transitivity.
  • (b) No. B⁺ = {B, C, D} under this cover — doesn't include A. B does not determine A.
  • (c) No. D⁺ = {D}. D doesn't determine anything else.
  • (d) Yes. {A, D}⁺ ⊇ A⁺ = {A, B, C, D} (A alone already closes over everything via the transitivity chain). AD → BC follows.
  • (e) Yes. B → C (given), C → D (given), so by transitivity B → D. Combined with the trivial B → B (reflexivity), we get B → BD by the union rule.

Practice tip: any "does F entail X → Y?" question reduces to computing X⁺ under F and checking whether Y is a subset.

Apply It

In the Interview

FD theory shows up wherever an interviewer wants to test whether you can reason about a schema, not just build one.

"How do you find the primary key of a table you've never seen?" A weak candidate says "look at the column named id." A stronger answer: identify attributes that never appear on the right side of any FD (must be in every key), compute the closure of that set, and grow only if needed. When the closure covers all attributes, you have a superkey; trim it to minimality and you have a candidate key. This is the exact algorithm a schema-linter or SQL query optimizer uses under the hood.

The subtle question. "Given R(A, B, C, D) with FDs AB → C, C → D, D → A, is this table well-designed?" First identify the candidate keys (there's more than one), then check whether every non-trivial FD has a superkey on its left — the BCNF test. This exact exercise appears on graduate exams and FAANG interviews with regularity. The trick that catches people: when candidate keys overlap, a deceptive FD like D → A can look benign but violate BCNF. Being fluent with closure calculations makes this a 60-second answer, not a 20-minute struggle.

"Should I trust an auto-generated schema from an AI tool?" Increasingly common. The answer: run the closure test on every FD implied by the schema. If any left-hand side is not a superkey and the RHS is non-prime, you have anomaly bait. AI-generated schemas frequently over-normalize or under-normalize because they don't reason about FDs directly; verifying them by hand is the review skill.

Rule of thumb.

  • •Every schema-review conversation contains a hidden question: which FDs govern this table, and does every one of them have a superkey on the left?
  • •Finding a key is a closure computation, not a guess — start from the "never on the right" attributes.
  • •A minimal cover is the atomic rule set — normalization decisions are only as good as the closures they're built on.

If you can hold "which FDs govern this table, and does every one have a superkey on the left?" in your head while reading someone else's DDL, you're doing what a senior database engineer does.

2026 Status

In 2026: What Has Changed

Functional dependencies are the theory behind a question every 2026 engineer asks: what actually enforces this key?

  • Candidate keys are discovered, not declared — by probing uniqueness, reading index statistics, and testing dependencies against real data.
  • Keys are enforced by constraints and indexes, never by documentation. A functional dependency with no UNIQUE index behind it is a hope.
  • Surrogate versus natural keys is an engineering trade-off (join width and stability against meaning), not a purity test.
  • FDs are what the optimizer uses to eliminate redundant joins and to prove that a GROUP BY cannot change the answer.

Every table has at least one candidate key. If nobody wrote it down, the database is enforcing something different from what the team believes.
