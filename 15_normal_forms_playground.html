Normal Forms and Decomposition

Prepared by Dr. Gorkem Kar

Functional dependencies tell you what a schema promises. Normal forms tell you whether the schema keeps those promises without making you pay for it in anomalies. Normalization is the process of taking a relation, finding the FDs it violates, and decomposing it — splitting one table into several — until every remaining table represents exactly one subject and every non-key fact depends on the whole key, nothing but the key.

Foundations

The Cost of a Messy Table

Imagine a single table that stores student enrollments, course titles, and instructor departments all at once, one row per enrollment. It works — until someone updates a course title and has to remember to update every row that mentions that course, or deletes the last student enrolled in a course and accidentally loses the fact that the course exists at all. These are anomalies: update anomalies (the same fact stored redundantly, risking contradiction), insertion anomalies (you can't record a fact — like a new course — without an unrelated fact, like a student), and deletion anomalies (deleting one fact accidentally deletes another).

Normalization is the systematic cure. Each normal form (1NF, 2NF, 3NF, BCNF) is a stricter promise about how non-key attributes may depend on the key. As you move up the hierarchy, you eliminate a specific category of redundancy — and with it, a specific category of anomaly.

Foundations

The First Three Steps

1NF — Atomic Values

A relation is in First Normal Form if every attribute holds a single, indivisible value — no repeating groups, no comma-separated lists, no arrays packed into one cell. This is the entry price of being a relation at all; nothing below this is really "relational" in the formal sense.

2NF — No Partial Dependencies

A relation is in Second Normal Form if it's in 1NF and every non-prime attribute (one that isn't part of any candidate key) depends on the entire candidate key, not just part of it. This only matters when a candidate key is composite (more than one attribute) — if every key is a single attribute, 2NF is automatic. A partial dependency is a non-prime attribute that depends on only a subset of a composite key.

3NF — No Transitive Dependencies

A relation is in Third Normal Form if it's in 2NF and no non-prime attribute depends transitively on a candidate key — that is, there's no non-prime attribute determining another non-prime attribute. Formally, for every non-trivial FD X → Y, either X is a superkey, or every attribute in Y is prime (part of some candidate key). That second clause — the "or Y is prime" escape hatch — is exactly what separates 3NF from the stricter BCNF below.

FormRequirementAnomaly it removes
1NFEvery attribute is atomic (single-valued).Cells storing hidden lists/repeating groups.
2NF1NF, and every non-prime attribute depends on the whole key.Partial-dependency redundancy on composite keys.
3NF2NF, and no non-prime attribute depends on another non-prime attribute.Transitive-dependency redundancy (a fact-about-a-fact).
BCNFEvery non-trivial FD's determinant is a superkey — no exceptions for prime attributes.The last remaining redundancy 3NF's "prime" exception allows.

Each level is strictly stronger than the last: every relation in BCNF is in 3NF, every relation in 3NF is in 2NF, every relation in 2NF is in 1NF. The reverse doesn't hold.

Foundations

BCNF: The Strict Boundary

Boyce-Codd Normal Form removes 3NF's one escape hatch. Under 3NF, a violation X → Y is tolerated if Y happens to be a prime attribute — part of some candidate key. BCNF doesn't care: for every non-trivial functional dependency X → Y in the relation, X must be a superkey. Full stop.

This only produces a different verdict from 3NF when a relation has two or more overlapping candidate keys — a table with a single key, or with several keys that share no attributes, will always get the same 3NF and BCNF verdict. When keys overlap, an FD can have a non-superkey determinant whose right-hand side still happens to be prime, satisfying 3NF while violating BCNF. That's the gap the next worked example walks through in full.

Why not always insist on BCNF? BCNF decompositions aren't always dependency-preserving — sometimes checking a constraint requires joining tables back together, which is slower and easier to get wrong at write time. Many production schemas deliberately stop at 3NF for exactly this reason. Normalization theory gives you the tools; using them is a judgment call.

Which brings us to the honest ending. Production systems normalise to 3NF or BCNF and then denormalise on purpose — and the only thing that separates engineering from accident is a written reason and a refresh strategy. The cell below makes the trade-off cost visible.

Decomposition

Decomposition and the Chase

Decomposing a relation means splitting it into two or more smaller relations. The whole point of normalization only works if the split is lossless — joining the pieces back together with a natural join must reproduce exactly the original rows, no more, no fewer. A lossy decomposition can manufacture rows that were never in the original data, which is worse than the redundancy you were trying to fix.

The fast test: for R decomposed into R1 and R2, the join is lossless if and only if the intersection R1 ∩ R2 is a superkey of at least one of the two pieces. If neither piece's key equals (or is determined by) the shared attributes, the join can produce spurious combinations.

When the intersection test doesn't cleanly apply (a three-way decomposition, or an ambiguous case), fall back to the general chase test: build a tableau with one row per decomposed piece, fill unmatched attributes with distinct placeholder symbols, then repeatedly apply each FD to equate symbols across rows. If any row's placeholders all resolve back to the original tuple, the decomposition is lossless.

Decomposition

Dependency Preservation

Losslessness isn't the only property worth checking. A decomposition is dependency-preserving if every original functional dependency can still be verified by checking constraints locally, within a single decomposed table — without needing to join tables back together first. Losing this property doesn't corrupt data, but it means the database can't enforce a business rule with a simple per-table constraint; you'd need a trigger or application-level check that joins across tables.

Every BCNF decomposition is guaranteed lossless. Not every BCNF decomposition is guaranteed dependency-preserving — the SID/CID/IID example above is the classic case where splitting to BCNF genuinely loses the ability to check {SID,CID} → IID without a join. Some decompositions get you both properties simultaneously (the ENROLL example in the widget below is one), but you should always check dependency preservation independently — it isn't automatic just because a decomposition is lossless.

Applying the intersection-is-key test

Round 1 split ENROLL into R1(CourseID, Instructor, Department) and R2(StudentID, CourseID, Grade).

R1 ∩ R2 = {CourseID}. Is CourseID a superkey of R1? Yes — CourseID alone is R1's candidate key (CourseID → Instructor, Department). ✓ Lossless.

Round 2 further split R1 into R1a(Instructor, Department) and R1b(CourseID, Instructor).

R1a ∩ R1b = {Instructor}. Is Instructor a superkey of R1a? Yes — Instructor is R1a's candidate key (Instructor → Department). ✓ Lossless.

Both splits pass the intersection-is-key shortcut, so the full three-way decomposition {R1a, R1b, R2} is lossless — joining all three back together on their shared attributes exactly reproduces ENROLL.

Anomalies present in the original ENROLL table

Update anomaly
If Alice moves departments, every row where Instructor = Alice must be updated. Miss one, and the table contradicts itself about which department Alice belongs to.
Insertion anomaly
You can't record that a new course exists, or which instructor teaches it, until at least one student has enrolled — there's no row to hold CourseID/Instructor/Department without a StudentID.
Deletion anomaly
If S1 is the only student enrolled in MATH201 and that enrollment row is deleted, the fact "Bob teaches MATH201 for the Math department" disappears along with it.
Worked Examples

Worked Example: Classifying a Schema

Given R(StudentID, CourseID, StudentName, CourseTitle, Grade) with FDs StudentID → StudentName, CourseID → CourseTitle, StudentID, CourseID → Grade.

Candidate key: {StudentID, CourseID} — its closure covers all attributes, and nothing smaller works. Is R in 1NF? Yes, every cell is atomic. Is R in 2NF? No — StudentID → StudentName and CourseID → CourseTitle are both partial dependencies on the composite key, since StudentName and CourseTitle are non-prime and each depends on only part of the key.

Decompose to fix it: Student(StudentID PK, StudentName), Course(CourseID PK, CourseTitle), Enrollment(StudentID FK, CourseID FK, Grade). Each of the three resulting tables is independently verified BCNF — every FD in each piece has a superkey on its left.

Lesson: normalization proceeds by identifying the specific FDs that violate each level and decomposing to remove them. Each decomposition introduces a join, but restores integrity.

Worked Examples

Worked Example: A 3NF Table That Is NOT in BCNF

This is the classic example that separates 3NF from BCNF — it requires a relation with two overlapping candidate keys, otherwise 3NF and BCNF coincide.

Consider R(StudentID, CourseID, InstructorID) with FDs StudentID, CourseID → InstructorID (a student takes a given course from exactly one instructor) and InstructorID → CourseID (an instructor teaches only one course).

Candidate keys: {SID, CID}⁺ covers all three attributes. {SID, IID}⁺: start {SID, IID}, apply IID → CID to add CID, giving {SID, IID, CID} — also covers everything. So R has two overlapping candidate keys: {SID, CID} and {SID, IID}. All three attributes are prime.

Is R in 3NF? Check each FD: SID, CID → IID — LHS is a superkey, fine. IID → CID — LHS is not a superkey (IID alone can't determine SID), but CID is prime (it belongs to {SID, CID}), so 3NF's escape hatch permits it. 3NF: satisfied.

Is R in BCNF? BCNF drops the escape hatch — IID → CID has a non-superkey determinant, full stop. BCNF: violated.

Decomposing to fix it — split on the offending FD into R1(InstructorID PK, CourseID) and R2(StudentID, InstructorID) — is lossless (R1 ∩ R2 = {InstructorID}, the key of R1), but the FD SID, CID → IID can no longer be checked without joining R1 and R2 back together. Dependency preservation is lost. This trade-off — a cleaner schema but a harder-to-enforce constraint — is exactly why many working architects deliberately stop at 3NF for schemas with overlapping candidate keys.

Worked Examples

Worked Example: Testing a Decomposition for Losslessness

Given R(A, B, C, D) decomposed into R1(A, B, C) and R2(C, D), with FDs {A → B, B → C, C → D}.

Intersection: R1 ∩ R2 = {C}. Is C a superkey for R1 or R2? For R2(C, D): {C}⁺ = {C, D} — that's all of R2, so C is a superkey (in fact the only key) of R2. Lossless. ✓

Alternative check via the chase test (more general, and what you fall back on for three-way decompositions): build a tableau with one row per piece, mark unmatched attributes with distinct placeholder symbols, then apply each FD to equate symbols across rows. Only C → D finds matching values (both rows agree on C), which forces D to equal in both rows — collapsing the tableau back to the original tuple. Lossless either way.

Practice Problems

1. Classify R(A, B, C, D)

Given R(A, B, C, D) with FDs { AB → C, A → D, D → B }, find all candidate keys and the highest normal form satisfied.

▸ Reveal answer

{A}⁺: A → D adds D, then D → B adds B, then AB → C adds C. Closure = {A, B, C, D}. {A} is the unique candidate key.

2NF check: the only candidate key {A} is a single attribute, so there are no partial dependencies to worry about — 2NF holds automatically. 3NF/BCNF check: D → B has determinant D, which is not a superkey ({D}⁺ = {D, B}, doesn't cover A or C) — a violation for both 3NF and BCNF since B is non-prime. Highest normal form: 2NF.

2. Overlapping keys

Given R(A, B, C) with FDs { AB → C, C → A }, find all candidate keys and classify.

▸ Reveal answer

{A,B}⁺ = {A,B,C} (full) — candidate key. {B,C}⁺: C → A adds A, giving {A,B,C} — also a candidate key. Two overlapping candidate keys: {A,B} and {B,C}. All three attributes are prime.

3NF check: AB → C — LHS is a superkey, fine. C → A — LHS is not a superkey, but A is prime (part of {A,B}) — 3NF's escape hatch applies. 3NF holds. BCNF check: C → A has a non-superkey determinant — BCNF fails. Highest normal form: 3NF.

3. Not even 2NF

Given R(A, B, C, D) with FDs { A → B, C → D } and candidate key {A, C}, classify R, then propose a lossless BCNF decomposition.

▸ Reveal answer

{A, C} is the only candidate key, and it's composite. Both A → B and C → D are partial dependencies — B depends on just A (part of the key), D depends on just C (part of the key). 2NF already fails, so R is only in 1NF.

Decompose: R1(A, B) with key {A}, and R2(C, D) with key {C}. Each piece is independently verified BCNF. Losslessness: R1 ∩ R2 = {} — an empty intersection means this particular pair doesn't pass the intersection-is-key shortcut directly, but since the original key {A,C} splits cleanly with A determining R1 and C determining R2 with no attribute shared, the join of R1 × R2 on no common column reconstructs exactly the cross-product implied by the two independent FDs — lossless here because the two halves never overlapped in the first place.

4. 3NF with two overlapping keys

Given R(A, B, C) with FDs { AB → C, C → A } — wait, that's problem 2's schema. Instead: given R(A, B, C) with FDs { AB → C, C → B }, find all candidate keys and classify.

▸ Reveal answer

{A,B}⁺ = {A,B,C} — candidate key. {A,C}⁺: C → B adds B, giving {A,B,C} — also a candidate key. Two overlapping keys: {A,B}, {A,C}. All attributes prime.

3NF: AB → C — LHS superkey, fine. C → B — LHS not a superkey, but B is prime — escape hatch applies. 3NF holds, BCNF fails (same shape as the SID/CID/IID worked example). Highest normal form: 3NF.

5. Design your own BCNF decomposition

Given R(OrderID, ProductID, ProductName, Quantity) with FDs { OrderID, ProductID → Quantity, ProductID → ProductName }, classify R and decompose it to BCNF.

▸ Reveal answer

Candidate key: {OrderID, ProductID}. ProductID → ProductName is a partial dependency (ProductName is non-prime, ProductID is only part of the key) — 2NF fails, so R is only in 1NF.

Decompose: OrderLine(OrderID, ProductID, Quantity) with key {OrderID, ProductID} — BCNF, the only FD's LHS is the whole key. Product(ProductID PK, ProductName) — BCNF. Losslessness: intersection is {ProductID}, which is the key of Product — lossless. Dependency preservation also holds: both original FDs are checkable locally, one per table, without any join.

Apply It

In the Interview

Normalization questions test whether you can look at a schema and predict exactly where it will break — not just recite definitions.

"Is this table normalized?" A weak answer names a normal form without justification. A strong answer finds the candidate keys first, then walks the hierarchy: check 1NF (atomic values), then 2NF (any non-prime attribute depending on only part of a composite key?), then 3NF (any non-prime attribute depending on another non-prime attribute?), then BCNF (does every non-trivial FD's determinant hold a superkey, no exceptions?). Stop at the first level that fails and name the specific violating FD.

The subtle question. "Here's a 3NF schema — is it also in BCNF?" The honest answer requires checking whether the relation has overlapping candidate keys; if it does, 3NF and BCNF can diverge, and you need to name the specific FD whose determinant isn't a superkey. If keys don't overlap, 3NF and BCNF coincide and the answer is automatically yes. This is precisely the SID/CID/IID pattern — interviewers use it because it's the cleanest way to test whether you actually understand candidate keys, not just pattern-match "looks normalized."

"Should we normalize this further, or denormalize for performance?" A senior answer doesn't treat this as binary. Decompose to remove genuine anomaly risk (usually up through 3NF/BCNF for anything users write to directly), but recognize that every decomposition adds a join at read time and can lose dependency preservation. The right call depends on write frequency, consistency requirements, and query patterns — not a rule that "more normalized is always better."

Rule of thumb.

  • •Find the candidate keys first — every normal form is defined relative to them.
  • •Each level up the hierarchy removes one specific category of redundancy; name which one.
  • •A decomposition must be checked for losslessness AND, separately, for dependency preservation — passing one doesn't guarantee the other.

If you can walk from "here are the FDs" to "here's the highest normal form, and here's the exact violating dependency if it's not BCNF" without hesitating, you're doing what a senior database engineer does in a design review.

2026 Status

In 2026: What Has Changed

Normalisation is no longer an all-or-nothing rule — it is the deliberate first half of a two-part decision.

  • Normalise to 3NF/BCNF, then denormalise deliberately. The second half of that sentence is what production warehouses actually do.
  • Star schemas and one-big-table designs are controlled denormalisation: duplicated columns kept on purpose, optimised for reads.
  • Materialised views and columnar compression make some redundancy cheap, which changes the economics of normalising everything to the theoretical maximum.
  • Lossless-join and dependency preservation are the safety checks: a decomposition you cannot join back is data loss, and one that drops an FD is a constraint you can no longer enforce.

Normal forms are not a destination; they are the vocabulary you use to justify a denormalisation.
