Why Databases? From Files to DBMS

Prepared by Dr. Gorkem Kar

Every app on your phone, every AI assistant that remembers a conversation, every payment that clears before you leave the coffee shop — all of them run on a database. And yet the software that makes this possible is invisible by design. To understand it, we have to go back to a simpler question: why does a database even exist? What does it do that a folder of files on a laptop cannot?

Foundations

Why Databases?

The problem is not the data itself. The problem is how the data is managed. When you store information in simple files, you are responsible for keeping everything organized, accurate, and safe. A Database Management System, or DBMS, is a piece of software that takes those responsibilities off your plate. It shifts the burden of "how to store it" away from the programmer and into a system designed specifically to handle the messiness of real-world information.

Foundations

The Problem with Redundancy

In a basic file-based system, different departments often keep their own records. The registrar has a file for student grades. The housing office has a file for dorm assignments. The billing office has a file for tuition.

This leads to redundancy. The student's name, ID, and home address are stored in all three places. On the surface, this seems like a minor annoyance: you are just using extra disk space. But the real cost is not storage. The real cost is inconsistency.

Imagine a student moves to a new apartment. They call the registrar to update their address. The registrar updates their file, but the billing office still has the old address. A month later, the tuition bill goes to the wrong house. This is the "Data Redundancy Trap." When information is scattered across different files, you no longer have a single source of truth. You have several different versions of reality, and you can never be sure which one is right.

Foundations

The Three Data Anomalies

When you use a file-based approach, you run into three specific types of errors called anomalies. These are not just bugs. They are structural failures that happen because the data is not organized properly.

The Update Anomaly

This happens when you have redundant data and try to change it. If a professor's phone number is listed in ten different rows because they teach ten different classes, you have to update all ten rows. If you miss one, the data is now broken. A user looking at the first row sees one number, while a user looking at the last row sees another.

The Insertion Anomaly

This happens when you cannot record a piece of information because you are missing a different piece of information. Suppose your file structure stores "Course Data" and "Student Data" in the same row. If the college creates a new Advanced Robotics course but no students have signed up yet, you might not be able to add the course to the file at all. The system expects a student ID to create a record. You shouldn't need a student to exist just to acknowledge that a course exists.

The Deletion Anomaly

This is the most dangerous one. It happens when deleting one piece of information accidentally destroys something else you wanted to keep. Imagine a small department where only one student is majoring in Physics. If that student drops out and you delete their record, you might accidentally delete the information about the Physics major itself, including the department's office number and the dean's name. By removing the student, you have wiped the department off the map.

Foundations

The ACID Guarantee

To solve these problems, a DBMS provides a set of properties known as ACID. Think of ACID as a contract between you and the database. The database promises that no matter what happens, your data will stay reliable.

Atomicity

This is the "all or nothing" rule. If you are transferring money from your savings account to your checking account, two things must happen: the money leaves savings, and the money enters checking. If the power goes out after the first step but before the second, the money vanishes. A DBMS ensures that if any part of the transaction fails, the whole thing is undone. It is as if the transfer never started.

Consistency

The database has rules, called constraints. A rule might say "a bank balance cannot be negative" or "every student must have a valid ID." Consistency means the database will never allow an operation that breaks these rules. If a transaction tries to create an illegal state, the DBMS will reject it.

Isolation

In the real world, thousands of people use a database at the same time. Isolation ensures that even if two people are editing the same record at the exact same millisecond, they don't trip over each other. To each user, it feels like they are the only ones using the system. The database handles the traffic jam behind the scenes.

Durability

Once the database tells you a change is saved, it is permanent. Even if the server crashes or the building loses power five seconds later, the data will still be there when the system reboots. The change is "durable" because it has been written to non-volatile storage.

Foundations

Schema vs. Instance

When you work with a DBMS, you have to separate the "shape" of the data from the "content" of the data. This is the difference between a schema and an instance.

The Schema is the blueprint. It defines what the data will look like, what the columns are named, and what type of information goes into them. For example, a schema for a student might look like this:

Student = { ID: Integer, Name: String, GPA: Float }

The schema rarely changes. You design it once and leave it alone for a long time.

The Instance is the actual data sitting in the database at a specific moment in time. If you have 500 students enrolled today, those 500 rows are the current instance. If five students graduate and ten new students join tomorrow, you have a new instance, but the schema remains exactly the same.

Think of it like a house. The architectural drawings are the schema. The people and furniture inside are the instance. You can move the furniture every day, but changing the blueprints requires a major renovation.

Worked Examples

Worked Example: Anatomy of a Failed Bank Transfer

The ACID properties are easiest to internalize by watching them fail. Consider two customers, Alice and Bob, and a single shared account. Alice starts a transfer of $200 from Account A to Account B. At the same instant, Bob queries the total balance across both accounts.

Without a DBMS, the sequence might play out like this:

TimeEvent
T = 0msAlice's transaction reads Account A ($500).
T = 1msAlice's transaction subtracts $200 and writes $300 back.
T = 2msBob's query reads Account A ($300) and Account B ($100). It reports a total of $400.
T = 3msAlice's transaction reads Account B ($100), adds $200, and writes $300.

The true total was always $600. Bob observed $400 — a value that never legally existed. This is an isolation failure specifically, but notice how it interacts with atomicity: had the system crashed at T = 2ms, the $200 would have vanished entirely.

A DBMS solves this in two related ways. Alice's whole transfer is bundled into a transaction — atomicity says the two writes either both happen or neither does, so a crash mid-transfer is not fatal. And isolation says Bob's query either sees the state before Alice's transaction started OR the state after it committed, never the in-between. Every one of the four ACID letters is doing concrete work here.

Worked Example: When Schema Change Breaks the Instance

Suppose a small ecommerce startup defines its Customer schema like this:

Customer(customer_id INT, name VARCHAR, email VARCHAR)

Six months later, the marketing team wants to record how each customer heard about the company. An engineer adds a column:

ALTER TABLE Customer ADD COLUMN source VARCHAR NOT NULL;

The migration fails on every existing row. Why? Because those rows already exist in the instance — they have no value for the new source column — and the schema is now forbidding NULL there. The schema change contradicts the current instance.

There are two clean fixes: (a) allow NULL for existing rows, or (b) provide a DEFAULT 'unknown' so the DBMS can back-fill. Both work because they leave the existing instance in a valid state under the new schema.

The lesson: schema and instance are separate but coupled. Change the schema and you have implicitly asked the DBMS "is every row in the current instance still valid?" A well-designed migration answers "yes" up-front.

Worked Examples

Worked Example: Watching a Flat File Break Under Load

Picture a small school running enrollment out of one CSV file. Two staff open it simultaneously in different spreadsheets.

  • Staff A adds a new student on row 401 and saves.
  • Staff B, unaware, adds a different student, also on row 401, and saves 30 seconds later.

The second save silently overwrites the first. The first student is now missing from the file, with no error and no log.

Every problem in this scene has a DBMS-shaped solution:

  • Concurrent writes destroying each other → the DBMS uses locks or MVCC (Multi-Version Concurrency Control) to serialize conflicting writes.
  • No audit trail of what changed → the DBMS keeps a transaction log; every commit is recorded.
  • Referential integrity (e.g. "you can't enroll a student who doesn't exist") → foreign-key constraints reject the write at the database level, not in application code that someone might forget to run.

A CSV is just data. A DBMS is data plus guarantees. This whole course is about learning to reason with those guarantees.

Practice Problems

1. Match each scenario to the ACID property being violated

(a) A power outage during a transfer leaves $500 debited from Account A but never credited to Account B.
(b) Two ATMs read the same account balance simultaneously and both withdraw the full amount, resulting in a negative balance the bank never intended.
(c) A committed order confirmation vanishes after the server reboots the next morning.
(d) A trigger on Order inserts a row into Invoice, but the invoice row is missing the required customer_id field.

▸ Reveal answer
  • (a) Atomicity — the transfer is not all-or-nothing.
  • (b) Isolation — concurrent transactions saw each other's uncommitted state.
  • (c) Durability — committed data must survive crashes.
  • (d) Consistency — an integrity constraint (customer_id NOT NULL) is violated.

2. The redundant office number

A flat CSV file stores one row per (Student, Course, Instructor) combination. If Professor Chen changes offices, in how many rows must the office number be updated? What is this called, and what does normalization do about it?

▸ Reveal answer

The office number must be updated in every row where Chen teaches — potentially dozens. This is the update anomaly. Normalization (Week 7) fixes it by moving Instructor data into its own table with office as a column, so a single update reaches every reference automatically.

3. Why a DBMS for a library system?

You're designing a small library system. Users can borrow books. Argue in two sentences why a DBMS is appropriate here, referencing at least two of the four ACID properties.

▸ Reveal answer

Example: "Concurrent borrows of the last copy must be serialized so two users don't both succeed (isolation), and once a return is recorded the transaction must survive a server restart even if the user's browser closed immediately (durability)." Other valid pairs: atomicity + consistency (a borrow that fails halfway should not leave the book flagged as checked-out; a return should not violate any inventory constraint).

Apply It

In the Interview

The concepts in this reading show up in almost every senior-engineer database interview — usually as a warm-up round that filters out anyone who has memorized SQL syntax without understanding the model underneath.

"Walk me through ACID." The strong answer doesn't just recite four letters. It says: "Atomicity is the transaction boundary — a group of operations that commit together or roll back together. Consistency is the invariant boundary — the database enforces constraints so no committed state is illegal. Isolation is the concurrency boundary — concurrent transactions produce a result equivalent to some serial execution. Durability is the crash boundary — once the DBMS acknowledges a commit, the data survives power loss. Together they turn a shared file into a shared source of truth."

"When would you NOT use a relational database?" Interviewers love this because it filters people who treat SQL as a hammer. Legitimate reasons to reach for something else: schemas that legitimately don't fit tables (deeply nested documents, graph queries where every hop is a join), massive write throughput with weak consistency needs, extreme geographic distribution where eventual consistency is acceptable, or specialized workloads (time-series, search, vector similarity). The nuance: even those cases usually keep a relational database somewhere as the source of truth.

"What is an anomaly?" In a file-based interview question ("here's a flat schema, what's wrong with it?"), the expected answer names the three anomalies — update, insertion, deletion — and points at the specific columns that trigger each. This is exactly the vocabulary that normalization (Week 7) uses to justify its rules.

Rule of thumb.

  • •Every interview conversation about "why is a database better than a file?" is really about ACID and about the three anomalies.
  • •Being able to name them precisely, and give one concrete example of each, is the difference between a junior answer and a senior one.
2026 Status

The Modern Database Landscape

The move from simple files to a DBMS is the move from manual labor to automation. In a file-based system, the programmer has to write code to prevent redundancy, code to handle simultaneous updates, and code to make sure data isn't lost during a crash. This makes applications fragile and difficult to maintain.

By using a DBMS, you outsource those problems to a system that is mathematically proven to handle them. You define your schema to eliminate redundancy and prevent anomalies. You rely on ACID properties to handle crashes and heavy traffic. This separation of concerns is what allows modern software to handle massive amounts of data without collapsing under its own weight. The database becomes the stable foundation, allowing you to focus on building the features that actually matter to your users.

The relational database was invented in 1970 by E.F. Codd. Its resilience is striking: the same core model that powered mainframe applications in the 1980s runs your bank, your airline, and the AI model you talked to this morning. What has changed is where that model runs and what it stores alongside relational tables.

By 2026, the DBMS landscape looks something like this:

  • Managed cloud databases (Amazon Aurora, Google Cloud SQL, Azure Database, Neon, Supabase, Turso) are the default deployment target. You rarely install a database on a server anymore; you provision one from a console and connect via a URL.
  • Analytical databases (Snowflake, BigQuery, Databricks, DuckDB) sit alongside transactional ones. The same SQL you learn in this course runs on both — the difference is the storage engine underneath and the workload each is tuned for. DuckDB in particular has become the default local analytical engine and now runs inside notebooks, CLIs, and even the browser (via WebAssembly).
  • Vector search has been folded into mainstream relational databases via extensions and native types: pgvector on PostgreSQL, sqlite-vec on SQLite, MySQL 9's native VECTOR type, and equivalents in SQL Server and Oracle. Embeddings from language models are stored right next to relational columns, and ORDER BY embedding <-> query_vec is now a normal query pattern for retrieval-augmented AI systems.
  • AI-assisted SQL is everywhere. Every mainstream IDE and cloud console will write a query for you from a natural-language prompt. That makes the theory in this course more important, not less — because you now have to read and debug SQL you did not write, and know when the AI is wrong.

None of this changes what a database is. The ACID guarantees, the schema/instance split, the anomalies that arise without a DBMS — all still apply, whether you deploy on a laptop or across five continents. This course teaches the mental model that survives every layer of tooling built on top.
