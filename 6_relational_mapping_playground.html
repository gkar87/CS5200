An ER diagram is a picture. A database engine needs tables. This playground turns the seven-step mapping algorithm into something you run, break, and fix — every CREATE TABLE below executes against a real, in-browser SQLite engine.

Overview

The translation from an ER diagram to a relational schema is not creative work — it's a deterministic algorithm developed in the 1970s and refined ever since. Once you know the seven steps, you can look at any ER diagram and produce working tables in minutes. This page walks through the formal vocabulary, the four kinds of keys, the algorithm step by step (each with a live cell you can edit and run), and three worked examples that show where the "just add an FK" mental model gets more interesting: multi-strategy inheritance, deceptively simple 1:1 relationships, and a broken mapping you have to diagnose yourself.

How to use the cells: Every gray box below is a real SQLite database. Click Run to execute the SQL as written, or edit it first — try changing a value, breaking a constraint on purpose, or adding your own row. Each cell starts from a fresh, isolated database, so nothing you do here can break another cell.
Foundations

The Formal Language of Relations

In conversation we say "table," "row," and "column." The formal relational model uses more precise terms, because they carry mathematical weight.

Formal termWhat you'd call it informallyDefinition
RelationTableA set of tuples. Because it's a set, row order doesn't matter, and every row must be unique — no formal relation can contain two identical rows.
TupleRowA single instance of an entity or a relationship.
AttributeColumnA named role that a data value plays in the relation.
DomainColumn type + rulesThe set of all possible values an attribute can take — not just "integer," but "integer between 0 and 120" for an Age domain.

The structure of a relation is written as a relation schema:

R(A1, A2, ..., An)

where R is the relation's name and each Ai is an attribute. For a student database:

STUDENT(StudentID, Name, Email, Major)

The Four Kinds of Keys

In a set, every element must be distinguishable from every other. In a database, keys do that job. Understanding the hierarchy below is the difference between a schema that works and one that silently corrupts itself the first time someone updates a row.

1 Superkey

Any set of attributes that, taken together, uniquely identifies a tuple. If you have a SocialSecurityNumber, that's a superkey. If you combine SocialSecurityNumber and FavoriteColor, that's also a superkey — it's "super" because it's a superset of a unique identifier, not because it's efficient.

2 Candidate Key

A minimal superkey — remove any attribute and it stops being unique. SocialSecurityNumber is a candidate key. SocialSecurityNumber + FavoriteColor is not, because FavoriteColor is unnecessary.

3 Primary Key

Out of all your candidate keys, you choose one to be the official identifier for the relation. Every other table that wants to reference this one points at the primary key.

4 Foreign Key

An attribute in one table that points to the primary key of another. This is how relationships are created, and it enforces referential integrity: you cannot have a pointer to something that doesn't exist. If table A has a foreign key pointing to "Employee 502" in table B, table B must actually contain Employee 502.

Run this cell to see a table with two independent candidate keys — a common source of confusion, since people assume a table can only have one:

Both emp_id and ssn are declared UNIQUE NOT NULL, so either one alone can serve as the row's identity. SQLite happily enforces both — but only one, here emp_id, is the actual PRIMARY KEY. ssn remains a candidate key that lost the vote.

The ER-to-Relational Mapping Algorithm

Turning a visual ER diagram into a set of tables follows a specific, seven-step algorithm. Skip a step and you lose information about how your entities relate to each other.

StepER constructWhat happens to it
1Strong entityOne relation. Choose a candidate key as PK. Flatten composite attributes to their components.
2Weak entityOne relation. Owner's PK becomes an FK. New PK = owner's PK + partial key.
31:1 relationshipFK on the totally-participating side — or merge the two entities if conceptually inseparable.
41:N relationshipNo new table. PK from the "1" side becomes an FK on the "N" side.
5M:N relationshipNew junction table. Two FKs, together forming the composite PK.
6Multivalued attributeNew relation: the attribute value + the parent's PK.
7N-ary relationship (3+ entities)New relation with the PKs of all participants as FKs.
The Algorithm

1 Strong Entities

For every regular entity, create a relation. Include all simple attributes. Choose one candidate key as the primary key. A composite attribute (like Address made of Street, City, Zip) gets flattened — you keep the components, not the parent attribute.

2 Weak Entities

Weak entities have no primary key of their own — they depend on an owner. Add the owner's PK as an FK in the new table, and set the weak entity's PK to owner's PK + partial key. Because the weak entity can't exist without its owner, the FK is usually declared ON DELETE CASCADE.

If a relationship involves three or more entities at once, create a new relation with the primary keys of all participants as foreign keys. A Sale that ties together Customer, Product, and Store is a three-way relationship — it cannot be decomposed into three separate binary relationships without losing information about which combinations actually happened.

Worked Example: A Full ER-to-Relational Mapping

A university has Departments (dept_code, name, budget). Each department employs many Professors (prof_id, name, phone_numbers [multivalued], hire_date) — every professor works for exactly one department. Professors advise many Students (student_id, name, gpa), and a student may have multiple advisors (M:N). Professors have Dependents (name, relationship, dob) — a dependent's name is unique only within a given professor and can't exist without one. Some professors are Tenured (tenure_date, endowed_chair_name), some are Adjunct (hourly_rate) — every professor is exactly one of these; there are no generic professors.

4M:NAdvises(prof_id, student_id) junction table
5Multivalued attributeProfessorPhone(prof_id, phone)
6Specialization (disjoint, total)Professor.kind discriminator with a CHECK constraint tying it to tenure_date / hourly_rate

Worked Example: Handling Inheritance — The Three Strategies

When your ER diagram includes subclasses (Employee → Engineer, Secretary), you have to decide how to represent that "Is-A" relationship in a system that only understands flat tables. Say Employee(EmpID, Name, Salary) specializes into Engineer(SoftwareStack) and Secretary(TypingSpeed).

StrategyShapeProsCons
1. Multiple Tables
(class-specific)		Employee(EmpID,Name,Salary)
Engineer(EmpID,SoftwareStack)
Secretary(EmpID,TypingSpeed)		Clean, no wasted columns, subclass-specific NOT NULL works, overlapping specializations are trivial (a row can exist in both).Every subclass query needs a join back to Employee.
2. Single Table
(type discriminator)		Employee(EmpID,Name,Salary,SoftwareStack,TypingSpeed,JobType)Fast — no joins at all.Wasted NULLs (an engineer's TypingSpeed is always empty); can't use a plain NOT NULL to require "engineers must have a stack" without also blocking every secretary row.
3. Concrete Tables OnlyEngineer(EmpID,Name,Salary,SoftwareStack)
Secretary(EmpID,Name,Salary,TypingSpeed)		No joins, no NULLs, each table stands alone.Can't enforce "EmpID unique across all employees" without extra work; "list every employee" needs a UNION; a person who's genuinely both would need duplicated rows.

Worked Example: Detecting a Broken Mapping

Here's a schema someone actually shipped. Run it, look at what it lets you insert, and see if you can spot the ER structure it was trying to represent — and why the mapping is wrong.

broken_enrollment.sql
▸ Reveal the three problems

Problem 1 — natural-key collision: (student_name, course_code) as the primary key means two different students who happen to share a name become an instant collision the moment they take the same course. The mapping used a natural key where it should have introduced a surrogate student_id.

Problem 2 — update anomaly: student_dob and course_title repeat on every row that mentions that student or course. If Alice takes six courses, her date of birth is stored six times — and nothing stops those six copies from silently drifting apart.

Problem 3 — three entities conflated into one table: this single table is trying to be Student, Course, and Enrollment all at once. The fix is to decompose it back into three relations, each describing exactly one kind of thing.

The corrected decomposition — run it and notice that two different people named "Alice Kim" can now coexist without conflict:

corrected_3table_decomposition.sql

Rule of thumb: any time a table's non-key attributes describe more than one "kind of thing," you've found a mapping mistake worth undoing before you write data into it.

Practice Problems

1. Author / Book / Wrote / Chapter

An Author writes many Books (M:N, via Wrote, which carries a royalty_pct). Each Book has many Chapters (weak entity, partial key chapter_number). Map this ER fragment to relations.

▸ Reveal answer
Author(author_id PK, name, email)
Book(isbn PK, title, year)
Wrote(author_id FK, isbn FK, royalty_pct, PRIMARY KEY(author_id, isbn))
Chapter(isbn FK, chapter_number, title, PRIMARY KEY(isbn, chapter_number), FOREIGN KEY(isbn) REFERENCES Book ON DELETE CASCADE)

2. Product with multivalued tags

Show a wrong mapping and a right mapping for a Product entity with a multivalued tags attribute.

▸ Reveal answer

Wrong: a CSV string column, e.g. Product(product_id, name, tags) with tags='outdoor,camping,4-season'. Forces LIKE queries with no usable index, produces false substring matches, and has no controlled vocabulary.

Right: ProductTag(product_id FK, tag, PRIMARY KEY(product_id, tag)) — optionally with a lookup table Tag(tag PK) to enforce a controlled vocabulary.

3. Employee manages (self-referencing)

Map a 1:N recursive manages relationship on Employee. What changes if managers can co-manage the same subordinate (M:N)?

▸ Reveal answer

1:N: Employee(emp_id PK, name, salary, manager_id NULL REFERENCES Employee(emp_id)) — a self-referencing, nullable FK on the subordinate side (the classic adjacency-list pattern; NULL represents "no manager," e.g. the CEO).

M:N (co-management): needs its own junction table: Manages(manager_id FK, subordinate_id FK, PRIMARY KEY(manager_id, subordinate_id)), both FKs referencing Employee(emp_id).

4. Country ← Locates → Store, Country total

A Country "locates" many Stores (1:N), and every country in the database is required to have at least one store (total participation on the Country side). Where does the FK go, and does it enforce that rule?

▸ Reveal answer

The FK goes on Store (the "N" side, as always for 1:N): Store.country_code NOT NULL REFERENCES Country. This enforces "every store has a country" — but it does not enforce "every country has at least one store." Plain SQL has no native way to require a parent row to have at least one matching child. Options: application-level checks before allowing a country to be inserted without a store, a trigger that re-verifies on insert/delete, or a denormalized store_count column with a CHECK — each with real trade-offs. In practice, the honest answer is often "document the rule and accept application-level enforcement."

5. Reverse-engineer a broken table

Enrollment(student_id, student_name, student_email, course_id, course_title, professor_name, grade). What ER structure was this trying to represent, and what's wrong with the mapping?

▸ Reveal answer

Flaws: student attributes (name, email) and course attributes (title) are redundantly repeated on every enrollment row — an update anomaly (changing a professor's name means updating every enrollment row for every course they teach); an insertion anomaly (you can't represent a course that has zero enrollments yet); a deletion anomaly (deleting the last enrollment in a course silently loses that course's metadata); and professor_name is a plain string rather than a foreign key to a Professor table, so a professor's name typo can silently create a "new" professor.

Corrected:

Student(student_id PK, name, email)
Course(course_id PK, title, professor_id FK)
Enrollment(student_id FK, course_id FK, grade, PRIMARY KEY(student_id, course_id))
Apply It

In the Interview

Schema design is the most common single hour of a system-design interview at any company that touches data. Practicing the ER-to-relational algorithm makes you fast at what interviewers actually watch for.

The classic setup: design the schema for a ride-sharing app, Instagram, Slack, or a stock brokerage. You're expected to identify entities, cardinalities, primary keys, and foreign keys — usually without being prompted step by step.

What's actually being scored:

  • 1.Correct cardinality. User↔Ride should be 1:N, not 1:1 — a rider takes many rides over time. Getting the multiplicity wrong on the very first relationship you draw is a bad signal.
  • 2.Junction tables for M:N. Post↔Tag, Song↔Playlist — if you draw a direct FK for a many-to-many relationship, that's a tell that the algorithm hasn't been internalized.
  • 3.Weak entities and identifying relationships. OrderLine, Chapter, Comment — entities that only make sense in the context of an owner, with composite primary keys.
  • 4.Foreign-key referential actions. "What happens when a user deletes their account?" is really asking whether you know CASCADE / SET NULL / RESTRICT and can reason about GDPR-style deletion requirements.

The senior-level curveball: "How would this schema handle 100 million users? What do you denormalize first?" The answer interviewers want isn't "denormalize everything" — it's normalize the source of truth, and denormalize read-side projections for hot paths. Keep one clean, correct table as the system of record, and build fast, possibly-stale materialized views or caches on top of it for the queries that actually need to be cheap.

Practice suggestion: pick a product you use daily — DoorDash, GitHub, Notion, Robinhood — and sketch its schema in 10 minutes: 4–6 entities, every cardinality, every foreign key. Repeat with a different product five times. The algorithm becomes reflexive faster than you'd expect.

2026 Status

In 2026: What Has Changed

Mapping rules have not changed; the keys, the nullability and the temporal columns around them have.

  • Surrogate keys are the default (IDENTITY, UUIDv7), while natural keys still dominate integration and analytics schemas because they mean something to the business.
  • Soft deletes need a partial index — UNIQUE … WHERE deleted_at IS NULL — or a deleted row blocks reuse of the natural key forever.
  • Temporal and bitemporal tables (SQL:2011 SYSTEM_TIME, or a companion audit table) record not just what is true but when it was true.
  • Mapping a JSON column is the modern 'one extra attribute' escape hatch: cheap to add now, expensive to query and constrain later.

Mapping is where modelling decisions become constraints — and constraints are the only part of a schema an application cannot ignore.
