Relational Algebra

Prepared by Dr. Gorkem Kar

When you write SELECT ... FROM ... WHERE ..., the database doesn't run your query character by character — it first translates it into a small set of mathematical operators it can rewrite, reorder, and cost. This playground makes those operators tangible: drag through selection and projection, watch a join build itself row by row, and compute a real division against a live SQLite engine.

Foundations

Overview

If you learn SQL first, you learn what to type. If you learn relational algebra, you learn how the database actually thinks. Relational algebra treats data as sets and provides a specific, small set of operations to transform those sets into answers. It is procedural — it describes the step-by-step path to a result — which is exactly why a query optimizer can reason about it: rewrite one path into a cheaper, provably equivalent path.

Foundations

Filtering and Pruning: Selection and Projection

The two most basic operations in relational algebra are about narrowing down what you're looking at. Think of a large spreadsheet — you usually want to hide the rows you don't need, and hide the columns you don't need.

Selection (σ) filters rows. You provide a condition, and the operator returns only the tuples that satisfy it:

σdept='Sales'(Employees)

Projection (π) filters columns. If you only care about names and salaries out of twenty columns, projection strips the rest away:

πname,salary(Employees)

The real power comes from combining them — relational algebra is compositional, meaning the output of one operation is the input to the next:

πname(σdept='Sales'(Employees))

Foundations

Notice the Order: Filter First, Then Project

We filter the rows first, then we cut the columns. In a real database, this is usually the most efficient order: selection typically shrinks the row count dramatically before projection has to touch anything, so the engine moves less data overall. Flip the order and — as the next section shows — you can lose the very column you needed to filter on.

Combining Relations

Combining Tables: Products and Joins

Data is rarely stored in one giant table. We split it up to avoid repetition: students in one table, courses in another, a third to track who's enrolled in what. To answer any interesting question, we have to put these tables back together.

Cartesian Product (×)

The most basic way to combine tables is the Cartesian Product. This is a "dumb" operation — it takes every row of table A and pairs it with every single row of table B. If A has 10 rows and B has 10 rows, the product has 100 rows. Most of these pairings are nonsense.

Natural Join (⋈)

To make pairings meaningful, we use the Join. The Natural Join is the most common version — it looks for columns with the same name in both tables and pairs rows only when those values match.

natural_join.sql

Compare the row counts: the Cartesian product above has rows × rows; the join has only the rows where dept_id actually matches.

Theta Join

Sometimes you need to join on a condition other than "names match." This is a Theta Join — you might join Orders with Promotions where the order date falls between the promotion's start and end dates:

Orders ⋈start < order_date < end Promotions

Set Operations and Renaming

Because relations are mathematically sets, we can use standard set theory on them. These operations require union compatibility — a fancy way of saying the two tables must have the same number of columns, with matching types.

OperatorMeaningExample use
Union (∪)All rows from both tables, duplicates removedCustomers who bought something in January or February
Intersection (∩)Only rows that appear in both tablesCustomers who bought something in both January and February

The Rename Operator (ρ) and Self-Joins

Sometimes you need to compare a table to itself. Imagine a Staff table where one column is employee_id and another is manager_id. To find out who reports to whom, you have to join the table to itself — and without an alias, the database can't tell which copy of Staff a column reference means. The Rename operator (ρ) gives a table (or column) a temporary alias so the two copies stay distinguishable:

ρManagers(Staff) ⋈Staff.manager_id = Managers.employee_id Staff
rename_self_join.sql

In SQL, ρ is just a table alias (AS m). It's not optional here — Staff JOIN Staff ON ... with no aliases is ambiguous and won't parse.

Halfway checkpoint. You now have selection, projection, product, joins, set operators, and rename — six operators that cover 90% of everyday queries. Next: one more operator (division), then reasoning about which rewrites are safe and why the query optimizer cares.
Combining Relations

The Division Operator: The "For-All" Problem

The hardest operator to grasp is Division (÷). You reach for it whenever a question contains the words "all," "every," or "each."

Consider two tables: Requirements — the courses needed to graduate — and Completed — every course every student has finished. To find students who've finished all the requirements, you divide:

Completed ÷ Requirements

Mathematically, division returns the values in the first table that are associated with every value in the second. If a student is only associated with two out of three required courses, they're dropped. It's the logical inverse of the Cartesian product.

Reasoning About Algebra

Recognizing Equivalent Expressions

One of the most important skills in relational algebra is recognizing that there's often more than one way to write a query — and knowing which rewrites preserve the answer and which silently change it.

When Operator Order Matters

Consider πname(σdept='Sales'(Employees)). Would projecting first and filtering after give the same answer?

order_matters.sql
No — these are not equivalent. If we project only name first, the dept column disappears. The selection can't then find "Sales" because that data is already gone. Swapping projection and selection is only safe when the selection's condition references attributes that survive the projection.

When Operator Order Does NOT Matter

Other rewrites are always safe. Two selections in a row are provably the same as one selection with an AND condition:

σprice>100(σcolor='Red'(Products))  =  σprice>100 ∧ color='Red'(Products)
combine_selections.sql

The equals sign here is a mathematical identity — for any Products table, both expressions produce the same set of tuples. This distinction between safe and answer-changing rewrites is exactly what the query optimizer relies on: it only applies rewrites from a proven catalog of equivalence laws, never guesses.

The Optimizer's Rewrite Catalog

RuleEquivalenceCondition
Push selection past joinσc(R ⋈ S) ≡ σc(R) ⋈ Sc references only R's attributes
Combine adjacent selectionsσc1(σc2(R)) ≡ σc1∧c2(R)always safe
Push projection past joinπL(R ⋈ S) ≡ πL(R ⋈ πL'(S))L' = L's attributes from S, plus the join key
Commutativity of joinR ⋈ S ≡ S ⋈ Ralways safe (cost may differ)
Associativity of join(R ⋈ S) ⋈ T ≡ R ⋈ (S ⋈ T)always safe (cost may differ)

The optimizer searches this equivalence space and picks whichever equivalent plan has the lowest estimated cost.

Worked Examples

Worked Example: Translating "English → Algebra → SQL"

Question: "Find the names of students who received an A in a course taught by Professor Chen."

Given: Student(sid, sname, major), Enroll(sid, cid, grade), Course(cid, cname, prof).

Building from the inside out:

  1. Filter enrollments to only A's: σgrade='A'(Enroll)
  2. Filter courses to only Chen's: σprof='Chen'(Course)
  3. Join those two on the shared cid: σgrade='A'(Enroll) ⋈ σprof='Chen'(Course)
  4. Join to Student on sid: (above) ⋈ Student
  5. Project the name: πsname(…)
πsname(Student ⋈ (σgrade='A'(Enroll) ⋈ σprof='Chen'(Course)))

Every ⋈ in the algebra corresponds to a JOIN in SQL. Every σ corresponds to a WHERE conjunct. The final π is the SELECT list. DISTINCT mirrors the algebra's set semantics — algebra returns sets, SQL returns bags by default.

Worked Examples

Worked Example: Query Rewriting for Optimization

The optimizer's job is to find the cheapest algebra expression equivalent to your query. Consider:

πsname(σgrade='A'(Student ⋈ Enroll))

This joins the entire Student table with the entire Enroll table first, then filters. If Enroll has a million rows and only a hundred are A's, that's a huge intermediate join. Since grade='A' only touches attributes from Enroll, it can be pushed down past the join:

πsname(Student ⋈ σgrade='A'(Enroll))

Now the join happens on the hundred A-grade rows instead of a million. Same answer, dramatically less work — run both below and check the result sets match:

Apply It

Practice Problems

1. Employees in high-budget departments

Given Employee(eid, name, dept, salary) and Department(did, dname, budget), write a relational algebra expression returning the names of employees who work in departments with a budget over $1M.

▸ Reveal answer
πname(Employee ⋈dept=did σbudget>1000000(Department))

Step by step: (1) filter Department to only high-budget rows — σbudget>1000000(Department); (2) join with Employee on the department key — a theta join, since the attribute names differ (dept vs did); (3) project the name. The filter is pushed early — good practice, and exactly what an optimizer would do to your SQL.

2. Prove σc(R ∪ S) ≡ σc(R) ∪ σc(S)

Give a concrete example demonstrating this equivalence.

▸ Reveal answer

Proof intuition: a tuple t is in σc(R∪S) iff (t is in R or t is in S) AND t satisfies c. Distributing: (t in R AND satisfies c) OR (t in S AND satisfies c) — exactly the right-hand side.

Concrete example: R = {(1,'A'), (2,'B')}, S = {(2,'B'), (3,'C')}, predicate c: attr1 > 1.

LHS: σ(R∪S) = σ((1,A),(2,B),(3,C)) = (2,B),(3,C). RHS: σ(R)∪σ(S) = {(2,B)} ∪ {(2,B),(3,C)} = (2,B),(3,C). Equal. This equivalence lets the optimizer push selection past union — often useful with partitioned tables.

3. Translate SQL to algebra

SELECT DISTINCT c.name FROM Customer c JOIN Order o ON o.cid = c.cid WHERE o.total > 500 AND c.country = 'USA';

▸ Reveal answer
πname(σcountry='USA'(Customer) ⋈cid σtotal>500(Order))

Both selections have been pushed down past the join (safe, since each references only one side's attributes). This is what the optimizer would rewrite πname(σcountry='USA' ∧ total>500(Customer ⋈cid Order)) into — both are equivalent, but the pushed-down version is cheaper.

4. Semi-join vs. anti-join vs. division

Given Enrolled(sid, cid) and Required(cid), express "students who've taken at least one required course" (semi-join) and "students who've taken none of the required courses" (anti-join). Contrast both with division.

▸ Reveal answer

At least one (semi-join): πsid(Enrolled) ⋉ Required, equivalently πsid(Enrolled ⋈ Required). SQL: SELECT DISTINCT sid FROM Enrolled WHERE cid IN (SELECT cid FROM Required).

None (anti-join): πsid(Enrolled) − πsid(Enrolled ⋈ Required). SQL: WHERE cid NOT IN (...) (watch for the NULL caveat) or WHERE NOT EXISTS (...).

Every required course (division): πsid,cid(Enrolled) ÷ Required. Semi-join asks "any match?"; anti-join asks "no match?"; division asks "all matches?" — three quantifier flavors (∃, ¬∃, ∀), and the reason relational algebra needs three separate operators.

5. Is this rewrite valid?

Is πsname(σgrade='A'(Student ⋈ Enroll)) equivalent to πsname(Student ⋈ σgrade='A'(Enroll))? Justify.

▸ Reveal answer

Yes, equivalent. grade='A' references only the grade attribute, which comes exclusively from Enroll — this satisfies the push-selection-past-join rule: σc(R⋈S) ≡ R⋈σc(S) when c references only S's attributes. The second form is typically much faster: the selection shrinks Enroll before the join, meaning fewer comparisons and a smaller intermediate result.

Counter-example for the invariance rule: σsname='Alice'(Student⋈Enroll) cannot be pushed into Enroll, because sname is a Student attribute — Enroll has no such column. It can only be pushed into Student: σsname='Alice'(Student)⋈Enroll. The optimizer only pushes a selection into the side where its referenced attributes actually live.

Apply It

In the Interview

Relational algebra rarely appears by name in interviews, but its ideas show up constantly through the query optimizer.

"Explain how the query optimizer works." This question filters candidates aggressively. A weak answer says "it figures out the best plan." A strong answer says: "The parser produces a logical plan expressed in relational algebra. The optimizer applies rewrite rules from the algebra's equivalence laws — push selections down, reorder joins, combine adjacent projections — to enumerate equivalent plans. Then a cost model, using statistics like row counts, distinct values, and index availability, picks the cheapest." That signals staff-level depth.

The "why is my query slow?" question. Behind almost every query-tuning interview problem is one of a handful of algebra-level issues:

  • 1.Selection didn't push down past a join — filtered on billions of post-join rows instead of the source table pre-join. Fix: rewrite so the WHERE references only one side.
  • 2.Cross product masquerading as a join — a missing ON clause turns an intended INNER JOIN into a Cartesian product. A common accidental bug, catastrophic on big tables.
  • 3.Redundant projection — SELECT *-style patterns force the executor to move columns it never needs. Fix: name only what you use.
  • 4.Join order matters — three-way joins have factorial-many possible orders. The optimizer picks one, but if statistics are stale, it picks badly.

The "division operator" test. Interviewers occasionally ask "how would you find users who purchased every product in category X?" as a filter for people who know the for-all pattern. The elegant answer uses double NOT EXISTS or HAVING COUNT(DISTINCT ...) = (SELECT COUNT(*) FROM ...). Recognizing this as the SQL translation of relational division is worth calling out explicitly.

Rule of thumb: any interview conversation that touches "why is this slow?" or "why did the optimizer pick that plan?" is a conversation about relational-algebra equivalences and cost estimation. Speaking that language is exactly what a senior data engineer or database engineer sounds like.

2026 Status

In 2026: What Has Changed

Algebra used to be exam material. In 2026 it is how you predict what the optimizer will do to a query you did not write.

  • The optimizer rewrites your SQL. Reading σ/π/⋈ is how you predict which plan it will pick, and why pushing a selection down is always safe.
  • Verifying AI-written SQL is now a routine task; relational algebra is how you check that a generated query computes what it claims.
  • Decorrelation — rewriting a correlated subquery as a join or semi-join — is the single most common optimizer transformation.
  • EXISTS, IN and joins are not interchangeable. With NULLs in play they give different answers, and the algebra is what explains why.

You rarely write algebra, but you constantly read its consequences — in query plans, in rewrite rules, and in code review.
