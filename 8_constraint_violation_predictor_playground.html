DDL Constraints & the Constraint Violation Predictor

Prepared by Dr. Gorkem Kar

A constraint is a promise the database enforces for you, whether or not the application code remembers to check. This playground walks through every constraint type — read the DDL, read the statement, predict whether it passes or fails, then run it for real against a live SQLite engine and see if you were right.

Foundations

Overview

Every CREATE TABLE statement is really two things at once: a description of what the data looks like, and a set of rules about what the data is allowed to look like. Those rules — PRIMARY KEY, NOT NULL, UNIQUE, CHECK, FOREIGN KEY — are enforced by the engine itself, on every single write, regardless of which application, script, or careless intern is doing the writing. That's the whole point: application-level validation can be forgotten, bypassed, or buggy. A constraint declared in the schema cannot be.

How to use this page: gray boxes are real SQLite queries you can edit and run. Read the DDL and the statement underneath it, guess pass or fail before you click Run, then check yourself.
Foundations

Primary Key

A PRIMARY KEY is the constraint that says "this column (or set of columns) is the row's identity — no two rows may share a value, and the value must always be present." It combines uniqueness with a mandatory presence requirement, and a table may have exactly one.

primary_key_basic.sql
SQLite quirk worth knowing: in standard SQL (and in PostgreSQL, MySQL, SQL Server), PRIMARY KEY automatically implies NOT NULL — you never need to write both. SQLite is the exception: unless the column is declared with the exact spelling INTEGER PRIMARY KEY (which makes it an alias for the internal row id, where NULL means "auto-assign the next id" rather than "no value"), SQLite will silently accept NULL as a primary key value. This playground's cells spell out PRIMARY KEY NOT NULL explicitly wherever it matters, which is also the safest habit to carry into any engine.
Foundations

NOT NULL & UNIQUE

NOT NULL and UNIQUE are independent constraints that are easy to conflate with PRIMARY KEY — and with each other. NOT NULL only says "this column can't be empty." UNIQUE only says "no two rows can share this value" — but unlike PRIMARY KEY, a UNIQUE column is still allowed to be NULL, and most engines (SQLite and PostgreSQL included) allow multiple rows to all be NULL at once, since NULL is never considered equal to another NULL.

unique_allows_multiple_nulls.sql

A table can have many UNIQUE columns but exactly one PRIMARY KEY. Think of PRIMARY KEY as "the row's identity" and UNIQUE as "no duplicates allowed, but this isn't necessarily the identity."

Foundations

CHECK Constraints

A CHECK constraint enforces a domain rule — any boolean expression the engine evaluates on every insert or update. It's how you encode business rules like "age can't be negative" or "price must be positive" directly into the schema, so they can never be violated no matter which code path writes the row.

check_constraints.sql
CHECK constraint or application check? Push validation into the database with a CHECK constraint whenever the rule is invariant across the whole domain — "age between 0 and 150" doesn't change based on which part of the app is writing. Application-level checks are bypassed by admin scripts, bulk imports, and eventually direct database access; database-level constraints are not. This is a defense-in-depth argument, not an either/or — validate early in the application for a good user experience, and enforce again in the schema so the rule can never be silently skipped.

Foreign Keys & Referential Integrity

A FOREIGN KEY says "this column's value must match some row's primary key in another table — or be NULL, if the column allows it." This is referential integrity: the guarantee that you can never have a pointer to something that doesn't exist.

Referential Actions: CASCADE / RESTRICT / SET NULL

Foreign keys don't just block bad inserts — they also decide what happens when the row they point to is deleted. That decision is the ON DELETE clause, and it's a business-rule question dressed up as a technical one.

ActionWhat happens to the childrenTypical use
RESTRICT (the default)The delete is blocked outright while any child row still references the parent.The user cannot be deleted while orders exist — forces a "close account" flow that resolves order state first.
CASCADEDeleting the parent automatically deletes every dependent child row too.Rare for e-commerce (deletes real transaction history); common for dev/test seed data cleanup.
SET NULLChild rows survive, but the foreign key column is set to NULL.Orders should be preserved anonymously for accounting/tax reasons — the user has a right to be forgotten, but the business has a legal duty to keep transaction records.

Aside: Storing Money Correctly

This isn't a constraint type, but it's the question every schema-design conversation eventually hits: how do you store a currency amount? The wrong answer is FLOAT or DOUBLE — floating-point cannot exactly represent decimals like 0.10, so arithmetic on money silently drifts.

float_money_error.sql

The correct answers are DECIMAL(precision, scale) (a true fixed-point type in most production engines — PostgreSQL, MySQL, SQL Server) or storing an integer number of cents (or millicents for crypto amounts), so ordinary integer arithmetic is exact by construction. Bonus points for storing the currency code in its own column — $100 USD and €100 are not the same number even when they print the same.

Worked Example: Which Constraint Fires First?

When a single statement breaks more than one rule, a database does not hand you a list of everything wrong. It stops at the first constraint it evaluates and reports only that one. The practical consequence is easy to miss: fixing the error you were shown can reveal a second violation you never saw.

SQLite answers with the CHECK failure — even though student 99 does not exist and the foreign key is broken too. Uncomment the second insert (with a legal grade) and the foreign-key error appears at last. Neither row was ever stored, so the outcome is the same either way; what changed is only which rule the engine happened to name first.

The lesson for debugging: an error message names one constraint, not all of them. When a fix does not clear the failure, the statement was probably breaking more than one rule — reading the constraint names in the schema is more reliable than trusting the single message.

Apply It

Practice Problems

1. DDL for a movies table

Write DDL for a movies table with these rules: 4-digit ID, non-empty title (≤ 200 chars), release year between 1888 and 2100, an optional director name, and a duration in minutes that must be positive.

▸ Reveal answer
CREATE TABLE movies ( movie_id INT PRIMARY KEY CHECK (movie_id BETWEEN 1000 AND 9999), title VARCHAR(200) NOT NULL CHECK (LENGTH(TRIM(title)) > 0), release_year INT NOT NULL CHECK (release_year BETWEEN 1888 AND 2100), director VARCHAR(200), duration_min INT NOT NULL CHECK (duration_min > 0) );

Notes: title NOT NULL alone doesn't stop empty strings — add CHECK (LENGTH(TRIM(title)) > 0). director is nullable (matches "optional"). The PK CHECK enforces the "4-digit" rule as a domain constraint.

2. Choosing ON DELETE actions

Given orders(order_id PK, customer_id FK → customers, total), choose the appropriate ON DELETE action for each business rule:

  • "When a customer's account is closed, their order history should be preserved for financial reporting."
  • "You cannot delete a customer if they still have unpaid orders."
  • "When a test customer is removed during dev seeding, all their orders should be cleaned up too."
▸ Reveal answer

ON DELETE SET NULL — the order rows stay; customer_id becomes NULL, indicating "customer no longer exists." (Requires customer_id to be nullable.)

ON DELETE RESTRICT — the DBMS blocks the delete until the FK dependency is resolved. This is the default in most systems.

ON DELETE CASCADE — the delete propagates. Only appropriate when the child row is meaningless without the parent, or in dev/test setups. Rarely correct for financial data.

3. Which INSERTs succeed?

Given:

CREATE TABLE products ( sku CHAR(8) PRIMARY KEY, name VARCHAR(200) NOT NULL, price DECIMAL(10, 2) NOT NULL CHECK (price > 0), stock INT DEFAULT 0 CHECK (stock >= 0) );
  1. INSERT INTO products VALUES ('ABC12345', 'Widget', 9.99, 100);
  2. INSERT INTO products VALUES ('ABC12345', 'Gadget', 12.00, 50); (immediately after the previous)
  3. INSERT INTO products (sku, name, price) VALUES ('XYZ99999', 'Sample', 4.00);
  4. INSERT INTO products VALUES ('SHORT', 'Pen', 3.00, 10);
  5. INSERT INTO products (sku, name, price, stock) VALUES ('DEF00000', NULL, 5.00, 5);
▸ Reveal answer

1. Pass. All constraints satisfied.

2. Fail — PK violation. sku = 'ABC12345' already exists (from the previous insert).

3. Pass. stock is omitted, so DEFAULT (0) fills it in; 0 passes CHECK (stock >= 0).

4. Fail — CHAR(8) length mismatch. 'SHORT' is 5 characters; in strict mode, the DBMS rejects it, or pads to 8 ('SHORT ') which usually isn't what you want. Better: add CHECK (LENGTH(sku) = 8) or use CHAR(8) NOT NULL and enforce format in the application.

5. Fail — NOT NULL violation on name.

Portability note: item 4 is engine-dependent — some engines pad or silently truncate instead of rejecting, and SQLite specifically stores CHAR(n) without enforcing the length at all, since SQLite uses dynamic typing with no true fixed-width string type. If a fixed length genuinely matters, don't rely on CHAR(n) alone — add an explicit CHECK (LENGTH(sku) = 8), which every engine (including SQLite) will actually enforce.

4. Dropping RESTRICT for performance

Your teammate proposes dropping the RESTRICT referential action from a heavily-used FK because "the deletes are too slow with all these checks." What are the immediate and long-term consequences?

▸ Reveal answer

Immediate effect: parent rows can now be deleted while children still reference them. The children's FK columns will point to nonexistent parents — orphaned rows. The DBMS will no longer stop the delete, and no cascade or set-null takes over because they weren't defined.

Long-term risk: joins against the parent will silently drop these orphans (INNER JOIN), which shows up as "missing data" in reports. Queries assuming referential integrity will produce wrong results. Restoring integrity requires manually finding all orphans and either fixing them or deleting them.

The correct fix if RESTRICT is "too slow" is almost never to drop the constraint. It's to fix the delete pattern (batch deletes, index the FK column) or to consciously change the action to CASCADE or SET NULL with the business's approval.

5. PRIMARY KEY vs. UNIQUE

Given users(id INT PRIMARY KEY, email VARCHAR(200) UNIQUE, username VARCHAR(50) UNIQUE). Explain the practical difference between the two UNIQUE constraints and the PRIMARY KEY.

▸ Reveal answer

All three enforce uniqueness. The differences:

PRIMARY KEY: implicitly NOT NULL. There can be only one PK per table. It's the row's canonical identifier — foreign keys elsewhere will reference id.

UNIQUE on email: allows NULL (in most DBMSes, multiple NULLs are allowed because NULL ≠ NULL). If a user hasn't confirmed their email yet, this column can be blank. Other tables typically don't reference this column.

UNIQUE on username: same semantics as email — allows NULL, allows multiple NULLs (in standard SQL and PostgreSQL; SQL Server treats NULL differently and only allows one NULL per UNIQUE column).

Practical lesson: PRIMARY KEY = "the row's identity." UNIQUE = "no two rows can share this value, but this isn't necessarily the identity." A table can have many UNIQUE columns but exactly one PRIMARY KEY.

Apply It

In the Interview

DDL and constraints come up in every backend interview that touches persistence.

The schema-migration question. "How would you add a NOT NULL column to a users table with 100M rows?" The correct multi-step answer:

  1. ALTER TABLE ... ADD COLUMN foo INT DEFAULT 0 — the default backfills without a table rewrite in modern PostgreSQL and MySQL 8+.
  2. Backfill any nuanced values in batches.
  3. ALTER TABLE ... ALTER COLUMN foo SET NOT NULL — safe once every row is populated.
  4. Deploy the application code that writes to foo on new rows.

Naming this multi-step choreography is what separates a candidate who has shipped migrations from one who has only read about them.

The referential-action question. "A user deletes their account. What do you set on the foreign key from orders to users?" The right answer depends on business rules:

  • •CASCADE if orders should disappear with the user (rare for e-commerce; common for dev seeds).
  • •SET NULL if orders should be preserved anonymously (typical for accounting/tax reasons; users have a right to be forgotten but the business has a legal duty to keep transaction records).
  • •RESTRICT if the user cannot be deleted while orders exist (forces a "close account" flow that resolves order state first).

Interviewers listen for whether you frame this as a business-rule question, not a technical one.

The money-storage question. "How would you store a currency amount?" A candidate who says FLOAT or DOUBLE loses the round immediately — floating-point cannot exactly represent decimals like 0.10, so summing 100 cents can give 99.999...¢. Correct answers are DECIMAL(precision, scale) or storing integer cents (or millicents for crypto). Bonus points for mentioning currency codes as a separate column, because $100 USD and €100 are not comparable.

The "check constraint or application check?" debate. "Where should we validate that a user's age is between 0 and 150?" Push validation into the database with a CHECK constraint whenever the rule is invariant across the whole domain. Application-level checks are bypassed by admin scripts, imports, and eventually direct database access; database-level constraints are not. Framing this as a defense-in-depth argument is the mature answer.

2026 Status

In 2026: What Has Changed

Constraints have quietly grown into the most portable business-rule engine we have.

  • Generated columns (STORED or VIRTUAL) move derived values into the schema, where they can be indexed and checked.
  • Partial and expression indexes enforce rules a plain UNIQUE cannot — 'unique among live rows', or 'unique on lower(email)'.
  • Foreign-key actions (ON DELETE CASCADE / RESTRICT / SET NULL) are part of the design, not an afterthought, and can be deferred inside a transaction.
  • Row-level security turns an access rule into a constraint the engine enforces per row, instead of a WHERE clause every developer has to remember.

Rules enforced by the engine survive every application, every script and every AI assistant that ever touches the data. Rules enforced by code do not.
