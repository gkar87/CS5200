Single-Table SELECT: The NULL Trap Detector

Prepared by Dr. Gorkem Kar

SELECT is the first SQL you learn and the SQL you write most — and it's deceptively simple. Underneath, the same engine that runs your one-liner also runs the dashboards that drive a company. This playground is about the traps: three-valued logic, execution order, and the set-operation subtleties that separate someone who can write a query from someone who knows exactly what it returns.

Foundations

The Logical Flow of a Query

When you write a query, you usually start typing the word SELECT. The database doesn't. If you want to write efficient queries, you have to think in the order the engine actually executes them:

FROM → WHERE → SELECT → ORDER BY → LIMIT

The database first looks at FROM to find the table. Then it moves to WHERE to throw away rows you don't need. Only after the rows are filtered does it look at SELECT to decide which columns to show. Finally it handles ORDER BY and LIMIT to sort and trim the final list. The order you write SQL in is not the order the database runs it in — a distinction that explains several traps in this reading.

One practical consequence right away: SELECT * asks the database to pull every column from every filtered row. On a table with fifty columns and a million rows, that's a lot of data moved for nothing. Naming only the columns you need reduces the "width" of what has to move, which is often a bigger performance lever than people expect.

Foundations

The Logic of Nothing: Handling NULL

NULL doesn't mean zero, and it doesn't mean an empty string. It means the value is unknown or missing. This creates three-valued logic: instead of just True and False, every condition in SQL can also come out Unknown. A WHERE clause only keeps rows where the condition is True — Unknown is treated the same as False for filtering purposes, but it is not the same value.

The single most common SQL bug: WHERE column = NULL will never match anything, ever — not even other NULLs. Because NULL means "unknown," comparing anything to it (even another NULL) can only produce Unknown, never True. To find missing values you must use IS NULL or IS NOT NULL, which are special-cased operators, not ordinary comparisons.

Foundations

Refined Filtering: LIKE, BETWEEN, and IN

Exact-match equals signs are fine until real-world data gets messy. LIKE gives you pattern matching: % is a wildcard for any run of characters, _ is a wildcard for exactly one character. Name LIKE 'J%' matches "John" and "Jane"; Name LIKE '%son' matches "Jackson" and "Thompson."

BETWEEN and IN exist purely for readability and optimizer-friendliness: Age BETWEEN 18 AND 25 instead of two chained comparisons, Country IN ('USA','Canada','Mexico') instead of a chain of ORs.

The wildcard-in-your-data gotcha: if the value you're searching for itself contains a literal _ or %, a plain LIKE '%_%' will match far more than you intend, because SQL reads that _ as "any one character," not literally. The fix is an ESCAPE clause that designates a character to neutralize the wildcard.

Set Operations: Combining Results

Sometimes what you need isn't in one query's rows — it's the combination, overlap, or difference of two queries. That's UNION, INTERSECT, and EXCEPT (called MINUS in some systems).

OperatorMeaningSemantics
UNIONAll rows from both queriesSet — duplicates removed, requires a sort/hash
UNION ALLAll rows from both queriesBag — nothing removed, just concatenated
INTERSECTRows that appear in bothSet
EXCEPTRows in the first query, not in the secondSet

Removing duplicates is expensive — the engine has to sort or hash the entire combined result to find matches. UNION ALL skips that step entirely, which is why it's almost always faster than plain UNION when you don't actually need deduplication.

Dialect gap worth knowing: standard SQL also defines INTERSECT ALL and EXCEPT ALL — bag versions of intersection and difference, useful when duplicate counts matter (e.g. "how many extra signups did campaign A have over campaign B, per email"). PostgreSQL supports both. SQLite does not support either ALL variant — try it below and watch it fail with a plain syntax error.

Sorting and Trimming

Row order in a table is never guaranteed. If you need a specific order, you must say so with ORDER BY — including for multiple columns: ORDER BY LastName ASC, FirstName ASC sorts by last name first, then breaks ties by first name.

LIMIT trims the sorted result, and LIMIT ... OFFSET ... is the standard pagination pattern — LIMIT 10 OFFSET 10 skips the first ten rows and returns the next ten.

The pagination trap: if your ORDER BY key has ties — two rows with the exact same created_at — SQL makes no promise about which order the tied rows come out in. A page built from LIMIT 20 OFFSET 40 can legitimately return a different subset of the tied rows on a later run, on a different engine, or after a query-plan change, even though "ORDER BY created_at DESC" is technically satisfied both times. The fix is a deterministic tie-breaker: add a column that's guaranteed unique, like the primary key.

Worked Example: Reading a Query in Execution Order

You write this, top to bottom:

SELECT department, salary * 1.1 AS new_salary FROM employees WHERE hire_date >= '2025-01-01' ORDER BY new_salary DESC LIMIT 5;

By the standard execution order, the database evaluates it: FROM (source relation) → WHERE (filter — at this point new_salary doesn't exist yet) → SELECT (now the expression is computed and the alias introduced) → ORDER BY (the alias exists now, so this is legal) → LIMIT. Reasoning from that order, WHERE new_salary > 100000 should be illegal — the alias hasn't been created yet.

worked_execution_order_alias_trap.sql
SQLite quirk — it doesn't actually enforce this rule. Run the cell above and the second statement succeeds: SQLite falls back to resolving an unrecognized identifier in WHERE against a matching SELECT-list alias, as a non-standard convenience. Standard SQL, and strict engines like PostgreSQL, reject WHERE new_salary > 100000 exactly as the execution-order model predicts — that's the portable behavior to design around. The fallback only kicks in when there's no real column of that name; add a genuine new_salary column to the table and SQLite prefers the real column over the alias, silently changing what your query means. Treat "alias in WHERE" as a bug to avoid even on SQLite, not a feature to rely on.

This ordering is also why SELECT COUNT(*) FROM t WHERE x IS NULL counts NULLs but SELECT COUNT(x) FROM t does not — COUNT(x) runs during the SELECT projection step, which is exactly where NULLs get skipped by definition of the aggregate. COUNT(*) counts rows, full stop, regardless of what's NULL inside them.

Practice Problems

1. Which queries match != 'shipped'?

Table orders(id, customer_id, status) has rows with status values 'shipped', 'pending', 'cancelled', and some rows with status IS NULL. Which of these queries returns the same set of rows as WHERE status != 'shipped'?

(a) WHERE status IN ('pending', 'cancelled')   (b) WHERE NOT (status = 'shipped')   (c) WHERE status <> 'shipped' OR status IS NULL

▸ Reveal answer

None of the three returns exactly what WHERE status != 'shipped' does, because != silently drops NULL-status rows.

(a) matches the non-null non-shipped rows only — same result as !=. (b) is equivalent to != (NOT of UNKNOWN is UNKNOWN, dropped) — same result. (c) explicitly includes NULLs — this is a superset of the != result.

So (a) and (b) are equivalent to !=, and (c) is what you probably wanted (!= 'shipped' including NULL status). The universal lesson: != and NOT (=) drop NULLs; if you want them included, add OR ... IS NULL explicitly.

2. Is this legal?

You wrote SELECT DISTINCT dept, salary FROM employees ORDER BY name. Predict whether this query is legal, and why.

▸ Reveal answer

It depends on the dialect, and is best avoided. After SELECT DISTINCT, the result contains only the columns dept and salary — name has been projected away. ORDER BY runs after SELECT and DISTINCT, so it operates on the projected relation. Some dialects (PostgreSQL) reject the query because name is not in the SELECT list and DISTINCT was applied. Others (MySQL in loose mode) accept it, sorting by the pre-projected name in a way that's ambiguous when DISTINCT collapses rows.

Safe rewrite: include the sort column in SELECT, or sort by a column that IS in the projection.

3. Matching literal wildcard characters

You need to find all users whose usernames contain either an underscore _ or a percent sign % (both are LIKE wildcards). Which query works?

▸ Reveal answer
SELECT username FROM users WHERE username LIKE '%\_%' ESCAPE '\' OR username LIKE '%\%%' ESCAPE '\';

The ESCAPE '\' clause designates a character to escape the wildcards. Without it, LIKE '%_%' matches any username with at least one character (since _ means "any single character"). Any character can be chosen as the escape (backslash is conventional but arbitrary). This is a classic gotcha when searching data that itself contains SQL wildcard characters.

4. Five set operations on the same two lists

Given campaign_a = {alice, bob, alice} and campaign_b = {alice, carol}, predict the result of each:

(a) ... campaign_a UNION ... campaign_b   (b) ... UNION ALL ...   (c) ... EXCEPT ...   (d) ... EXCEPT ALL ...   (e) ... INTERSECT ...

▸ Reveal answer

(a) {alice, bob, carol} — set union deduplicates.

(b) {alice, bob, alice, alice, carol} — bag union keeps everything.

(c) {bob} — set difference. Alice appears in B, so all Alices in A are removed.

(d) {bob, alice} — bag difference removes ONE alice per matching alice in B (only one in B), leaving one alice + one bob in A.

(e) {alice} — set intersection collapses to a single alice.

The ALL variants matter when multiplicities are meaningful (e.g., counting duplicate signups). Note: as the Set Operations section above demonstrates live, SQLite doesn't actually implement EXCEPT ALL — this answer describes standard SQL semantics (PostgreSQL supports it natively), and the section above shows how to simulate it with a window function where it's missing.

5. Deterministic pagination

Write a query that returns the second page (page size 20) of employees ordered by salary descending, then by name ascending as a tie-breaker.

▸ Reveal answer
SELECT emp_id, name, salary FROM employees ORDER BY salary DESC, name ASC LIMIT 20 OFFSET 20;

ORDER BY salary DESC — highest paid first. , name ASC — alphabetize ties. LIMIT 20 OFFSET 20 — skip page 1 (rows 1–20), return rows 21–40.

A common pitfall: without a deterministic tie-breaker like the secondary name ASC, two runs of the same paginated query can return different rows for the same page if there are ties on salary. Always make ORDER BY deterministic when paginating.

Apply It

In the Interview

The single-table SELECT is the SQL equivalent of FizzBuzz — it screens out candidates who cannot write basic SQL, and rewards ones who understand its subtleties.

The screener question. "Find all users who signed up in January but never verified their email." The immediate trap is that "never verified" often means verified_at IS NULL. Candidates who write WHERE verified_at = NULL fail the screener silently — the comparison is Unknown, so the result is empty. Being fluent in IS NULL / IS NOT NULL is table stakes.

The follow-up. "Now return the top 20 sorted by signup date." A candidate who writes LIMIT 20 alone is correct only if the ordering is inherent — which it never is in SQL. Always pair LIMIT with ORDER BY, and for pagination, add a deterministic tie-breaker (ORDER BY signup_date DESC, user_id DESC) so page 2 doesn't repeat page 1's tail.

The three-valued logic gotcha. "For a status column that can be 'active', 'inactive', or NULL, does WHERE status != 'active' return the NULL rows?" No — NULL != 'active' is Unknown, which the WHERE drops. To include them, write WHERE status != 'active' OR status IS NULL, or use WHERE status IS DISTINCT FROM 'active' in PostgreSQL. This exact question appears in Meta, Google, and Amazon SQL screens with regularity.

The set-operation trap. "Given two query results, combine them and remove duplicates." A weak answer is "just use UNION." A strong answer says "use UNION ALL if I know there are no duplicates or want to preserve counts, because plain UNION forces a sort/hash to dedupe and can be 5-10x slower on large data." That performance instinct is what interviewers watch for.

A real-world SaaS scenario to practice. Given events(user_id, event_name, event_ts) with billions of rows:

  • •"Count users active in the last 7 days." → SELECT COUNT(DISTINCT user_id) FROM events WHERE event_ts > NOW() - INTERVAL '7 days'.
  • •"How would you make this fast?" → Index on event_ts, or a pre-computed daily active-user rollup. Recognizing that "we could denormalize this into a summary table" is the shift from junior to mid-level thinking.
2026 Status

In 2026: What Has Changed

Three-valued logic has not changed, but the ways it bites you have multiplied.

  • IS DISTINCT FROM and IS NOT DISTINCT FROM give NULL-safe comparison — the inequality that = and <> are not.
  • Order NULLs deliberately with NULLS FIRST / NULLS LAST rather than relying on whatever the engine defaults to.
  • JSON null is not SQL NULL. A JSON null survives extraction as a value, while a missing key extracts to SQL NULL — a distinction that quietly breaks filters.
  • Three-valued logic bites AI-written SQL hardest, because a generated NOT IN (…, NULL, …) returns zero rows instead of raising an error.

Most silent data bugs are not crashes — they are filters that quietly matched nothing, and NULL is almost always the reason.
